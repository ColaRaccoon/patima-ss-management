0518 수정계획: 매핑 관리 탭 성능 구조 개선

주문 시그니처와 광고 비용 시그니처가 시간이 지날수록 누적되고, 신규 주문/광고 데이터가 들어올 때마다 과거 전체 데이터를 다시 자동 매핑하는 구조를 개선하기 위한 다음 세션 인수인계 문서다. 목표는 원장 데이터는 보존하면서, 매핑 관리는 고유 시그니처 단위로 압축하고 재계산 범위를 신규/변경 데이터로 제한하는 것이다.

1. 문제 정의

현재 구조는 주문 데이터나 광고 데이터가 들어오면 원천 row를 계속 추가하고, 매핑 관리 화면 및 자동 매핑 로직에서 이 누적 데이터를 넓게 다시 읽는다. 데이터가 적을 때는 문제가 안 보이지만, 운영 기간이 길어질수록 탭 로딩과 재계산 시간이 선형으로 증가한다.

주문 쪽 병목

  • orderSourceSignatures와 orderItems를 매번 전체 순회한다.
  • 주문 동기화 후 신규 데이터만 보면 되는데 전체 주문 아이템을 다시 매핑한다.
  • 매핑 탭에서 시그니처별 usage/enrichment 계산을 위해 주문 아이템 전체를 다시 뒤진다.

광고 쪽 병목

  • adCampaignDailyCosts가 일별 광고비 원장인데 매핑 관리 대상처럼 쓰인다.
  • 광고 규칙 변경 시 과거 일별 row 전체를 다시 매핑한다.
  • 매핑 탭이 광고 비용 row 전체를 페이지 단위로 끝까지 가져온다.
핵심 판단: 이 문제는 단순히 오래된 row를 삭제하는 방식으로 해결하면 안 된다. 손익 계산과 과거 검증을 위해 원장 데이터는 보관해야 한다. 대신 "원장 데이터"와 "매핑 관리 대상"을 분리해야 한다.

3. 목표 구조

목표는 "원장 row는 계속 보존하고, 매핑 판단은 고유 시그니처/캠페인 단위에서만 수행"하는 구조다. 과거 row를 매번 재계산하지 않고, 원장 row는 이미 결정된 매핑 결과 또는 시그니처 참조를 따라간다.

주문

  • orderItems: 주문 원장. 손익 계산의 근거 데이터로 유지.
  • orderSourceSignatures: 매핑 관리 대상. 고유 상품명/옵션 조합 1건만 존재.
  • 신규 주문이 들어오면 해당 시그니처만 생성/갱신하고, 해당 신규 주문 아이템만 매핑.

광고

  • adCampaignDailyCosts: 일별 광고비 원장. 날짜별 비용/성과 데이터로 유지.
  • adCampaignSignatures: 새로 추가할 광고 매핑 관리 대상.
  • 캠페인명/캠페인ID 단위로 한 번 매핑하고, 일별 광고비 row는 이 시그니처를 참조.
기대 효과: 매핑 관리 탭 로딩량은 "누적 주문/광고 row 수"가 아니라 "고유 시그니처 수"에 비례한다. 자동 매핑 비용도 신규/변경 데이터 수에 가까워진다.

5. 백엔드 수정 계획

5.1 주문 동기화: 전체 재계산 제거

order-sync.service.ts에서 주문 업서트 루프 중 새로 생성/수정된 주문 아이템 ID와 시그니처 ID를 모은다. 루프가 끝난 뒤 전체 recalculateOrderMappingsForStore 대신 부분 매핑 함수를 호출한다. 

const touchedSignatureIds = new Set<string>();
const touchedOrderItemIds = new Set<string>();

// 주문 루프 안
touchedSignatureIds.add(signature.id);
touchedOrderItemIds.add(payload.id);

// 기존 전체 재계산 제거
// recalculateOrderMappingsForStore(draft, storeId);

recalculateOrderMappingsForTouchedItems(draft, {
  storeId,
  signatureIds: touchedSignatureIds,
  orderItemIds: touchedOrderItemIds,
});

5.2 주문 시그니처 요약 필드 갱신

upsertSignature 또는 주문 업서트 루프에서 시그니처의 요약 필드를 즉시 갱신한다.

  • usageCount: 신규 주문 아이템이면 +1. 기존 주문 아이템 업데이트면 증가시키지 않음.
  • firstSeenAt: 최초 생성 시 설정.
  • lastSeenAt: 매 동기화 시 최신 주문/결제 기준으로 갱신.
  • sampleExternalProductId, sampleOptionCode: 비어 있을 때만 채우거나 최신값으로 갱신.
주의: 기존 주문 아이템이 다른 시그니처로 이동하는 경우가 생기면 old signature의 usageCount 감소도 필요하다. 현재 키는 externalProductOrderId 기준 업서트이므로, 기존 item의 orderSourceSignatureId를 비교해야 한다.

수동 "전체 재계산" 버튼 또는 마이그레이션/복구용으로 기존 recalculateOrderMappingsForStore는 남긴다. 단, 주문 동기화 같은 자주 실행되는 경로에서는 호출하지 않는다.

ads.service.ts에서 업로드된 각 캠페인 row마다 AdCampaignSignature를 찾거나 생성한다. 매핑 판단은 이 시그니처에 대해 수행하고, 일별 row는 adCampaignSignatureId와 결과 스냅샷을 저장한다.

5.6 수동 매핑 저장 위치 변경

현재 광고 수동 매핑은 adCostIds를 받아 일별 row에 직접 저장한다. 변경 후에는 UI에서 선택한 row의 adCampaignSignatureId를 찾아 시그니처에 저장한다.

  • 신규 API 권장: POST /ad-campaign-signatures/batch-mapping
  • 기존 API 호환: /ad-campaign-costs/batch-mapping은 내부에서 signature ID로 변환
  • 수동 매핑 시 confirmedAt 설정
  • 동일 캠페인 향후 업로드 row는 해당 시그니처 매핑을 자동 상속

5.7 DatabaseService 장기 개선

지금 당장 1차 목표는 매핑 로딩/재계산 축소다. 하지만 데이터가 더 커지면 DatabaseService.write의 전체 clone, PostgreSQL 전체 truncate/insert도 병목이 된다.

장기 개선안은 다음과 같다.

  • 컬렉션 전체 저장 대신 row 단위 upsert/delete 메서드 추가.
  • 자주 조회되는 필드에는 JSONB expression index 또는 별도 column 추가.
  • 파일 모드와 PostgreSQL 모드의 동작 차이를 테스트로 고정.

  • 주문 시그니처와 광고 시그니처는 각각 서버 페이지네이션을 사용한다.

  • 광고 row 상세가 필요하면 선택한 캠페인 시그니처의 최근 사용 row만 lazy load한다.

7. 마이그레이션 계획

7.1 normalizeSnapshot 기반 자동 보정

현재 프로젝트는 별도 DB migration도 있지만, 런타임에서 normalizeSnapshot으로 누락 필드를 보정하는 패턴이 있다. 다음 필드는 기존 데이터에 기본값을 채워야 한다. 

normalized.adCampaignSignatures = Array.isArray(normalized.adCampaignSignatures)
  ? normalized.adCampaignSignatures
  : [];

normalized.orderSourceSignatures = normalized.orderSourceSignatures.map((item) => ({
  ...item,
  usageCount: typeof item.usageCount === "number" ? item.usageCount : 0,
  firstSeenAt: item.firstSeenAt ?? item.createdAt ?? null,
  lastSeenAt: item.lastSeenAt ?? item.updatedAt ?? null,
  sampleExternalProductId: item.sampleExternalProductId ?? null,
  sampleOptionCode: item.sampleOptionCode ?? null,
  sampleOptionManageCode: item.sampleOptionManageCode ?? null,
  lastAutoMappedAt: item.lastAutoMappedAt ?? null,
  mappingRuleHash: item.mappingRuleHash ?? null,
}));

7.2 기존 광고 row에서 시그니처 생성

최초 실행 또는 명시적 migration 스크립트에서 기존 adCampaignDailyCosts를 순회하여 adCampaignSignatures를 생성한다.

  • 키 후보 1순위: storeId + channel + campaignId
  • campaignId가 없으면: storeId + channel + normalizedCampaignName
  • 기존 수동 매핑 row가 있으면 가장 최근 row의 수동 매핑을 signature에 승격
  • 서로 다른 수동 매핑이 섞여 있으면 CONFLICT로 두고 사용자가 확인하도록 표시
  • 각 row에는 생성된 adCampaignSignatureId를 채움
마이그레이션 주의: 과거 광고 row에 날짜별로 서로 다른 수동 매핑이 있을 수 있다. 이를 무조건 하나로 합치면 과거 손익이 바뀔 수 있다. 충돌이 있으면 자동 병합하지 말고 별도 검토 대상으로 남긴다.

판매단위 별칭/ID 규칙 변경 미확정 시그니처만 재계산. 수동 확정된 것은 유지
캠페인 매핑 규칙 변경 미확정 광고 시그니처만 재계산. 과거 row 반영은 사용자가 선택한 기간에만 수행
수동 전체 재계산 관리 버튼으로만 수행. 작업량과 영향 기간을 UI에 표시
마감된 월 기본적으로 재매핑하지 않음. 필요 시 명시적 백필만 허용

9. 구현 순서

  1. 타입/DB 스키마 준비
    AdCampaignSignature 타입, DatabaseShape.adCampaignSignatures, createEmptyDatabase, STORAGE_TABLES, normalizeSnapshot 보정 추가.
  2. 프론트 전체 fetch 중단
    매핑 탭에서 주문/광고 목록을 처음부터 전부 가져오지 않도록 서버 페이지네이션 기반으로 변경. 이 단계만으로도 탭 로딩 체감 개선이 크다.
  3. 주문 시그니처 요약 필드 도입
    주문 동기화 시 usage/firstSeen/lastSeen/sample 값을 갱신하고, listOrderSourceSignatures에서 주문 아이템 전체 집계를 제거.
  4. 주문 증분 매핑 추가
    recalculateOrderMappingsForTouchedItems를 만들고 주문 동기화 경로에서 전체 재계산 호출 제거.
  5. 광고 캠페인 시그니처 도입
    광고 업로드 시 adCampaignSignatures를 업서트하고 row에는 adCampaignSignatureId 저장.
  6. 광고 매핑 UI/API 전환
    매핑 탭 광고 섹션은 adCampaignDailyCosts 대신 adCampaignSignatures를 표시.
  7. 규칙 변경 재계산 축소
    캠페인 매핑 규칙 변경 시 전체 광고 row가 아니라 미확정 광고 시그니처만 재계산.
  8. 마이그레이션/백필 스크립트
    기존 광고 row에서 시그니처 생성, 주문 시그니처 요약값 재구축 스크립트 작성.

10. 테스트 계획

영역 검증 내용
주문 동기화 신규 주문만 들어왔을 때 기존 과거 주문 아이템의 updatedAt이 불필요하게 바뀌지 않는지 확인
주문 수동 매핑 시그니처 수동 매핑 시 연결된 주문 아이템 매핑이 기존처럼 반영되는지 확인
주문 시그니처 목록 usageCount, sample product/option 값이 주문 아이템 전체 순회 없이 표시되는지 확인
광고 업로드 동일 캠페인을 여러 날짜 업로드해도 광고 시그니처는 중복 생성되지 않고 usage/lastSeen만 증가하는지 확인
광고 수동 매핑 한 캠페인 시그니처를 수동 매핑하면 이후 업로드 row가 해당 매핑을 상속하는지 확인
광고 규칙 변경 수동 확정된 광고 시그니처는 재계산으로 덮이지 않는지 확인
매핑 탭 로딩 주문/광고 데이터가 많아도 첫 API 요청이 1~2페이지 수준으로 끝나는지 확인
손익 계산 기존 adCampaignDailyCosts, orderItems 기반 집계 결과가 변경 전과 동일한지 샘플 기간 비교

기존 테스트 실행 명령: npm run test --workspace @patima/backend, 전체 타입 체크: npm run lint.

11. 주의점

  • 원장 row 삭제 금지: 과거 손익과 검증을 위해 orderItems, adCampaignDailyCosts는 보존한다.
  • 수동 매핑 우선: confirmedAt이 있는 주문/광고 시그니처는 자동 재계산이 덮어쓰면 안 된다.
  • 과거 손익 변경 주의: 새 매핑 규칙을 과거 row에 일괄 반영하면 이전 리포트 숫자가 바뀐다. 기본은 향후 데이터 적용으로 둔다.
  • 캠페인 ID 신뢰도: 광고 캠페인은 campaignId를 우선 키로 쓰되, 비어 있거나 바뀔 수 있는 경우를 대비해 normalizedCampaignName fallback을 둔다.
  • 충돌 자동 병합 금지: 기존 row 중 같은 캠페인인데 서로 다른 수동 매핑이 있으면 사용자 확인 대상으로 남긴다.
  • 페이지네이션 우선: 프론트에서 fetchAllRecordPages를 매핑 탭 기본 로딩에 다시 쓰지 않는다.
  • DB write 비용: 이번 개선 후에도 데이터가 아주 커지면 DatabaseService의 전체 snapshot 저장 구조가 다음 병목이 된다.
  • 호환성: 기존 API를 바로 제거하지 말고, 내부에서 신규 시그니처 구조로 변환하는 bridge 기간을 둔다.

12. 완료 기준

  • 매핑 관리 탭 진입 시 주문 시그니처와 광고 시그니처를 전체 로딩하지 않는다.
  • 주문 동기화 후 전체 주문 아이템 재계산이 실행되지 않는다.
  • 광고 업로드 후 신규 캠페인 시그니처만 생성/갱신된다.
  • 광고 규칙 변경 후 전체 adCampaignDailyCosts 재계산이 기본 실행되지 않는다.
  • 수동 매핑은 시그니처에 저장되고 향후 row에 상속된다.
  • 기존 손익 계산 결과가 동일 기간 기준으로 회귀하지 않는다.
  • 백필/전체 재계산은 관리자 의도적 작업으로만 실행된다.
한 줄 요약: 주문과 광고의 과거 row는 원장으로 남기고, 매핑 관리는 고유 시그니처 테이블에서 수행한다. 자동 매핑은 전체 재계산이 아니라 신규/변경 데이터 중심의 증분 처리로 바꾼다.
