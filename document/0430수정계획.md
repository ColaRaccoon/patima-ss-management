# 0430 광고 업로드 흐름 단순화 작업계획서

## 0. 이 문서의 위치

이 파일 하나만 보고 다음 세션에서 바로 작업에 들어갈 수 있도록 작성됨. 실제 파일/라인 번호, 변경 전/후 로직, 기존 코드 재사용 범위, 회귀 위험 포인트를 모두 담음. 실제 코드는 작성되어 있지 않으므로 그대로 따라 수정하면 됨.

---

## 1. 수정 배경 및 방향

### 1.1 배경
현재 광고 엑셀 업로드는 `프리뷰 생성 → 사용자 검토 → 승인(confirm)` 의 3단계로 분리되어 있음. 사용자 입장에서 "올린 후 확인해서 다시 누르는" 두 번의 액션이 필요하고, UI 영역도 (프리뷰 카드 + 행 상세 테이블) 2섹션을 차지함.

운영해 보니 검토 단계에서 사용자가 실제로 의미 있게 판단할 부분은 거의 없고, **요일 검증이 통과된 파일은 그냥 바로 적용**하는 것이 맞다는 결론.

### 1.2 변경 후 흐름
```
사용자가 reportDate 선택 + .xlsx 파일 N개를 한 번에 선택 (multi-select)
        ↓ "업로드" 버튼 클릭
파일 단위로 독립 처리
  ├─ 요일 검증 PASSED → 즉시 adCampaignDailyCosts에 append + state=CONFIRMED, isActive=true
  └─ 요일 검증 실패 → 불통과 목록에 파일명 + 사유 표시 (DB 저장 안 함)
        ↓
결과 표시: "통과 N건 / 불통과: file1.xlsx (요일 불일치) ..."
```

### 1.3 핵심 결정 사항 (이미 사용자와 합의됨)

1. **중복 체크 로직은 전부 폐기**.
   - 한 파일 안에서 같은 campaignId가 두 번 등장해도 통과
   - 같은 reportDate에 이미 확정 업로드가 있어도 통과 (그냥 append됨)
   - 같은 파일을 실수로 두 번 올린 경우 → 사용자가 업로드 히스토리에서 수동 삭제하는 것으로 처리

2. **여러 파일은 같은 날짜에 독립적으로 누적**.
   - 광고 엑셀은 보통 하루에 3개(서로 다른 광고 유형)를 합쳐서 하루치 데이터로 사용
   - 각 파일의 campaignId는 서로 다르므로 그냥 append하면 됨
   - "덮어쓰기/머지" 같은 모드 분기 필요 없음

3. **통과/불통과 기준은 오직 요일 검증 (`weekdayValidationStatus === "PASSED"`)**.
   - 매핑 결과(MAPPED/UNMAPPED/CONFLICT)는 통과/불통과와 무관. 매핑은 적용 후에 계속 보정 가능.

4. **불통과 파일은 DB에 저장하지 않음**. 응답으로 파일명과 사유만 반환.

5. **사용되지 않게 된 함수들은 우선 호출만 끊고 코드는 남겨둠**. 동작 확인 후 별도로 정리하는 2단계 접근. (한 번에 다 지우면 다른 곳에서 참조하던 게 깨질 위험)

6. **파일 입력 UI를 단일 multi-file selector로 변경**. 현재는 슬롯 3개에 하나씩 끼워 넣는 구조. 변경 후에는 `<input type="file" multiple>` 하나로 N개 동시 선택. **개수 제한 없음** (3개 고정 폐기). 향후 광고 종류가 늘어나도 그대로 대응 가능.

#### 3.1.2 헬퍼 메서드 추가 — `describeWeekdayFailure`

요일 검증 실패 사유를 사람이 읽을 수 있게 만드는 작은 헬퍼.

```typescript
private describeWeekdayFailure(
  status: "MISSING" | "MULTIPLE" | "MISMATCH",
  detectedWeekdays: string[],
  reportDate: string,
): string {
  if (status === "MISSING") {
    return "엑셀에 요일 정보가 없습니다.";
  }
  if (status === "MULTIPLE") {
    return `여러 요일이 혼재되어 있습니다 (감지: ${detectedWeekdays.join(", ")}).`;
  }
  // MISMATCH
  const expected = getWeekdayNameKo(reportDate);
  return `reportDate(${reportDate}, ${expected})와 엑셀 요일(${detectedWeekdays[0]})이 일치하지 않습니다.`;
}
```

#### 3.1.3 호출 안 되게 되는 메서드 — **남겨두되 그대로**

다음 메서드들은 본 작업으로 호출 경로가 끊김. **삭제하지 말고 그대로 둠**. 다음 단계에서 정리.

- `enqueueConfirm()` (라인 305~328) — `POST /ad-uploads/:uploadId/confirm` 핸들러가 호출. 일단 유지.
- `performConfirm()` (라인 330~423) — `enqueueConfirm`이 큐 콜백으로 사용. 모듈 init에서 retry executor로도 등록(`onModuleInit` 라인 53~58). 그대로 유지해야 retry 큐가 깨지지 않음.
- `assertNoDuplicateCampaignIds()` (라인 746~757)
- `assertNoCampaignIdOverlap()` (라인 759~777)
- `findDuplicateCampaignIds()` (라인 779~788)
- `summarizeCampaignIds()` (라인 790~793)

> **주의**: TypeScript의 `noUnusedLocals` / `noUnusedParameters` 가 strict 하면 미사용 private 메서드가 빌드 에러를 낼 수 있음. 빌드 후 에러 발생 시 해당 메서드들 위에 `// eslint-disable-next-line` 또는 삭제 결정. 일단은 빌드해 보고 결정.

#### 3.1.4 `performConfirm()` 내부 중복 체크 (라인 380~388) 처리

`performConfirm`은 호출 경로가 끊기지만 retry executor로 등록되어 있으므로 만약 호출되면 동작은 해야 함. 그런데 안에 중복 체크가 들어있음:

```typescript

this.assertNoCampaignIdOverlap(...)
```

**옵션 A** (권장): 그대로 둠. 어차피 호출 경로가 없으므로 영향 없음. 나중에 정리.

**옵션 B**: 라인 380~388 의 두 호출도 함께 제거. 이 경우 retry로 들어왔을 때도 중복 검사 없이 통과됨 → 정책과 일관됨.

→ **옵션 A 채택**. 변경 최소화 원칙.

```typescript
onSubmit={async (event) => {
  event.preventDefault();
  setErrorMessage(null);
  setSuccessMessage(null);

  if (!reportDate.trim()) {
    setErrorMessage("reportDate is required.");
    return;
  }

  if (selectedUploadFiles.length === 0) {
    setErrorMessage("Select at least one .xlsx file.");
    return;
  }

  setIsUploading(true);
  try {
    const succeeded: string[] = [];
    const failed: Array<{ fileName: string; reason: string }> = [];

    for (const file of selectedUploadFiles) {
      const formData = new FormData();
      formData.append("storeId", primaryStore.id);
      formData.append("reportDate", reportDate);
      formData.append("file", file);

      const response = await fetch("/api/ad-uploads/preview", {
        method: "POST",
        body: formData,
      });

      const payload = (await response.json().catch(() => null)) as {
        message?: string;
        fileName?: string;
        weekdayValidationStatus?: string;
      } | null;

      if (!response.ok) {
        failed.push({
          fileName: file.name,
          reason: payload?.message ?? "업로드 실패",

        continue;

      succeeded.push(file.name);
    }

    if (succeeded.length > 0) {
      setSuccessMessage(
        `${succeeded.length}개 파일이 업로드되었습니다: ${succeeded.join(", ")}`,
      );
      setSelectedFiles([]);                     // 빈 배열로 리셋 (slot 구조 폐기)
      setFileInputSeed((value) => value + 1);   // input 엘리먼트 리마운트로 표시값 클리어
      startRefresh(() => {
        router.refresh();
      });
    }

    if (failed.length > 0) {
      const failureLines = failed
        .map((item) => `${item.fileName}: ${item.reason}`)
        .join("\n");
      setErrorMessage(`불통과 파일:\n${failureLines}`);
    }
  } catch (error) {
    setErrorMessage(
      error instanceof Error ? error.message : "Failed to upload files.",
    );
  } finally {
    setIsUploading(false);
  }
}}
```

> `errorMessage` 가 멀티라인이 되므로 기존 표시 div(라인 254~256)에 `whitespace-pre-line` 클래스 추가 필요.

## 6. 회귀 위험 포인트 (반드시 확인할 것)

### 6.1 PREVIEW_PARSED 상태 잔존 데이터

기존에 만들어진 PREVIEW_PARSED 상태 레코드가 DB에 남아있을 가능성. 이 작업으로 새로 생성되지는 않지만, 기존 데이터는 그대로 있음.
- `Upload history` 에는 그대로 표시됨 (라인 224~225 필터: DELETED만 제외).
- `getAdUploadsPageData()` 에서 `previews: []` 로 비웠으므로 더 이상 프리뷰 카드로는 안 보임.
- 사용자가 "이전 프리뷰" 잔재를 정리하려면 업로드 히스토리에서 수동 삭제하거나, 별도 마이그레이션으로 일괄 DELETED 처리.
- **권장**: 첫 배포 시 일회성 정리 스크립트 또는 수동 SQL 실행 검토. 검증: `adExcelUploads` 에서 `state="PREVIEW_PARSED"` 행 수 확인.

### 6.2 `adUploadPreviewRows` 테이블 잔존 행

기존 PREVIEW_PARSED 업로드의 행들이 `adUploadPreviewRows` 에 남아있음. 이 작업 후로는 더 이상 쓰지도, 늘리지도 않음.
- 손익 계산 등 다운스트림에서 이 테이블을 참조하는지 확인 필요. (코드상 `ads.service.ts` 외부에서 참조하는 곳은 페이지 데이터 로딩 정도로 보이지만, 백엔드 다른 서비스에서도 grep 한 번 권장)
- 검증 명령: `grep -r "adUploadPreviewRows" apps/backend/src` 로 외부 참조 확인.

### 6.3 retry 큐의 PREVIEW_PARSED 의존

`onModuleInit` (라인 53~58) 에서 `AD_UPLOAD_CONFIRM` 타입 작업의 retry executor로 `performConfirm` 등록. 기존에 큐에 들어갔다가 실패해서 retry 대기 중인 작업이 있다면 → `performConfirm` 호출 → 라인 341 의 `state !== "PREVIEW_PARSED"` 체크에서 실패. 이 경우 재시도 영구 실패 상태. 일단은 운영상 큰 문제 안 됨 (사용자에게 직접 영향 없음). **단, 큐를 한 번 비우고 시작하는 것을 권장**.

### 6.4 `replacedUploadId`, `previewExpiresAt` 등 사용되지 않게 되는 필드

`AdExcelUpload` 의 `replacedUploadId`, `previewRuleSnapshotHash`, `previewOverrideSnapshotHash`, `previewCreatedAt`, `previewExpiresAt`, `previewState`, `requiresConfirm` 등은 의미를 잃음.
- 스키마(JSONB)에서 제거하면 기존 데이터 호환성 문제 → 그대로 두고 채움.
- 새 흐름에서는 `previewCreatedAt = nowIso()`, `previewExpiresAt = +7일`, `state = "CONFIRMED"`, `isActive = true` 로 채워서 저장 (3.1.1 코드 참고).

### 6.5 매핑 변경 시 기존 확정분과의 정합성

매핑 규칙이나 수동 오버라이드가 변경되면, 기존엔 프리뷰 단계에서 `previewRuleSnapshotHash` / `previewOverrideSnapshotHash` 검증이 있었음 (라인 365~377). 이제 즉시 적용이므로 이 검증은 의미 없음 — 단순히 업로드 시점의 매핑 결과로 저장됨. 사용자가 매핑 규칙을 수정한 뒤 영향받는 행을 다시 매핑하려면 기존의 `recalculateMappings()` API를 사용 (이미 존재, 라인 506).

### 6.6 부분 실패 시 트랜잭션

`databaseService.write` 안에서 `adExcelUploads.push` + `adCampaignDailyCosts.push(...)` 가 한 번에 일어나면 원자적. 그러나 `previewUpload()` 자체는 한 파일 처리 단위. 프론트가 N개 파일을 for 루프로 호출하므로 **중간 파일에서 실패해도 앞서 성공한 파일은 그대로 적용된 상태**.

→ 이게 의도된 동작. 부분 성공이 자연스러움. UI에서 "통과 N건 / 불통과 M건" 으로 명확히 표시.

### 6.7 프론트 mock data

`USE_AD_UPLOADS_MOCK_FALLBACK` 분기가 있음. mock 데이터에 PREVIEW_PARSED 행이 들어있다면, `getAdUploadsPageData()` 가 빈 previews를 반환하더라도 `Upload history` 에서는 보임. 이 자체는 OK. mock 데이터 별도 수정 불필요.

### 6.8 동시 업로드 race

같은 reportDate에 3개 파일이 거의 동시에 업로드되는 시나리오. 백엔드의 `databaseService.write`는 직렬 처리되므로 race 없음. 프론트의 for 루프도 순차이므로 OK.

```typescript
      message: "엑셀(.xlsx) 파일만 업로드할 수 있습니다.",
      errors: [{ field: "file", reason: "EXCEL_REQUIRED_COLUMNS_MISSING" }],
      fileName: originalFileName,
    });
  }

  // 2. 파싱
  const workbook = XLSX.read(file.buffer, { type: "buffer" });
  const sheet = workbook.Sheets[workbook.SheetNames[0]];
  const rows = XLSX.utils.sheet_to_json<string[]>(sheet, { header: 1, raw: false });
  const header = (rows[0] ?? []).map((value) => this.normalizeHeaderCell(value));

  AD_UPLOAD_REQUIRED_HEADERS.forEach((requiredHeader) => {
    if (!header.includes(this.normalizeHeaderCell(requiredHeader))) {
      throw new BadRequestException({
        success: false,
        message: "필수 엑셀 컬럼이 누락되었습니다.",
        errors: [{ field: requiredHeader, reason: "EXCEL_REQUIRED_COLUMNS_MISSING" }],
        fileName: originalFileName,
      });
    }
  });

  const campaigns = this.parseCampaignRows(rows, header);
  const detectedWeekdays = Array.from(
    new Set(campaigns.map((item) => item.weekday).filter(Boolean)),
  ) as string[];

  // 3. 요일 검증
  let weekdayValidationStatus: AdExcelUpload["weekdayValidationStatus"] = "PASSED";
  if (detectedWeekdays.length === 0) {
    weekdayValidationStatus = "MISSING";
  } else if (detectedWeekdays.length > 1) {
    weekdayValidationStatus = "MULTIPLE";
  } else if (detectedWeekdays[0] !== getWeekdayNameKo(reportDate)) {
    weekdayValidationStatus = "MISMATCH";
  }

  // 4. 불통과 시 즉시 throw (DB 저장 안 함)
  if (weekdayValidationStatus !== "PASSED") {
    throw new BadRequestException({
      success: false,
      message: this.describeWeekdayFailure(weekdayValidationStatus, detectedWeekdays, reportDate),
      errors: [{ field: "file", reason: "AD_UPLOAD_WEEKDAY_VALIDATION_FAILED" }],
      fileName: originalFileName,
      weekdayValidationStatus,
      detectedWeekday: detectedWeekdays[0] ?? null,
    });
  }

  // 5. 통과 — 즉시 확정 저장
  const snapshot = this.databaseService.getSnapshot();
  const activeConfirmedRows = this.getActiveConfirmedRows(snapshot, storeId, reportDate);

  const upload: AdExcelUpload = {
    id: createId(),
    storeId,
    sourceType: "NAVER_DA_XLSX",
    originalFileName,
    fileHash: hashBuffer(file.buffer),
    reportDate,
    detectedWeekday: detectedWeekdays[0] ?? null,
    weekdayValidationStatus,
    replacedUploadId: null,
    previewRuleSnapshotHash: getRuleSnapshotHash(snapshot, storeId),
    previewOverrideSnapshotHash: getOverrideSnapshotHash(snapshot, storeId),
    previewCreatedAt: nowIso(),
    previewExpiresAt: new Date(Date.now() + 7 * 86_400_000).toISOString(),
    state: "CONFIRMED",                // ← 변경
    isActive: true,                     // ← 변경
    createdAt: nowIso(),
    updatedAt: nowIso(),
  };

  const confirmedRows: AdCampaignDailyCost[] = campaigns.map((campaign) => {
    const normalizedCampaignName = normalizeText(campaign.campaignName);
    const inheritedOverride = this.findInheritedOverride(
      activeConfirmedRows,
      campaign.campaignId,
      normalizedCampaignName,
    );
    const mapping = evaluateAdMapping(
      snapshot,
      storeId,
      normalizedCampaignName,
      inheritedOverride ? getAdMappingOverride(inheritedOverride) : null,
    );
    return {
      id: createId(),
      uploadId: upload.id,                // 호환을 위해 유지 (AdUploadPreviewRow와 같은 모양)
      sourceUploadId: upload.id,          // adCampaignDailyCosts 의 핵심 필드
      storeId,
      reportDate,
      campaignId: campaign.campaignId,
      campaignName: campaign.campaignName,
      normalizedCampaignName,
      weekday: campaign.weekday,
      adType: campaign.adType,
      status: campaign.status,
      totalCost: campaign.totalCost,
      impressions: campaign.impressions,
      clicks: campaign.clicks,
      totalConversions: campaign.totalConversions,
      totalConversionSales: campaign.totalConversionSales,
      matchedRuleCount: mapping.matchedRuleCount,
      canonicalSalesUnitId: mapping.canonicalSalesUnitId,
      mappingReason: mapping.mappingReason,
      reasonNote: mapping.reasonNote,
      reasonNoteInherited: mapping.reasonNoteInherited,
      createdAt: nowIso(),
      updatedAt: nowIso(),
    };
  });

  // 6. DB 저장 — 한 번의 write 트랜잭션
  this.databaseService.write((draft) => {
    draft.adExcelUploads.push(upload);
    draft.adCampaignDailyCosts.push(...confirmedRows);
  });

  // 7. 감사 로그
  this.auditLogService.record({
    storeId,
    domain: "AD_UPLOAD",
    action: "CREATE",
    targetId: upload.id,
    actorIdentifier: "LOCALHOST_ADMIN",
    beforeJson: null,
    afterJson: {
      reportDate,
      originalFileName,
      confirmedRowCount: confirmedRows.length,
    },
  });

  // 8. 응답
  return formatApiSuccess({
    uploadId: upload.id,
    reportDate,
    detectedWeekday: upload.detectedWeekday,
    weekdayValidationStatus,
    status: "CONFIRMED",
    confirmedRowCount: confirmedRows.length,
  });
}
```

> **주의**: `AdCampaignDailyCost` 타입에 `uploadId` 필드가 있는지 `packages/shared/src/types.ts` 에서 먼저 확인. 기존 `AdUploadPreviewRow` 에는 있고, `AdCampaignDailyCost = AdUploadPreviewRow + sourceUploadId` 형태였음 (라인 1~8 import 참고). 그대로 들어가면 됨. 만약 `AdCampaignDailyCost` 가 `uploadId` 를 갖지 않는다면 위 매핑에서 제거.
