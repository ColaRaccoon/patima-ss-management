## 필수 선행

먼저 [0604_수동매핑_쓰기성능_공통지침.md](./0604_수동매핑_쓰기성능_공통지침.md)를 읽는다.

이 단계도 반드시 공통 지침의 서브 에이전트 루프를 따른다. 개발자 에이전트가 구현하고, 평가자 에이전트가 결함을 하나라도 발견하면 재작업을 지시하며, 평가자가 합격할 때까지 반복한다.

## 목표

큰 구조 변경 전에 저위험 낭비를 제거하고, 이후 단계의 성능 비교 기준을 만든다.

## 현재 문제

수동 매핑 저장 후 영향을 받은 주문/광고 날짜를 모아 순이익 요약을 재계산한다. 그런데 날짜 목록이 비어 있어도 `ProfitSummaryService.recalculateStoreDateList()`가 실행되어 `writeCommitted()`를 한 번 더 탄다.

사용량 0인 미매핑 시그니처를 매핑할 때 특히 낭비가 크다.

또한 rawPayload가 대부분 남아 있어 전체 snapshot 비용이 커진다. 이 단계에서는 실 데이터 삭제를 실행하지 말고, 정리 절차와 안전장치만 명확히 한다.

## 작업 범위

필수 수정:

1. `ProfitSummaryService.recalculateStoreDateList()` 또는 그 호출 전 단계에서 `dates.length === 0`이면 DB write 없이 즉시 성공 응답을 반환한다.
2. `OrderMappingService.recalculateProfitSummariesForOrderSignatures()`에서 날짜를 dedupe하고, 비어 있으면 profit summary refresh를 호출하지 않는다.
3. `AdsService.recalculateProfitSummariesForAdIdentifiers()`에서 날짜를 dedupe하고, 비어 있으면 profit summary refresh를 호출하지 않는다.
4. 필요한 경우 `refreshStoreDateListBestEffort()`도 빈 날짜를 안전하게 no-op 처리한다.
5. 성능 측정용으로 `scripts/report-db-size.mjs` 실행 결과를 문서화할 수 있는 짧은 README 또는 기존 scripts README 보강을 검토한다.

선택 수정:

- 환경변수로 켤 수 있는 write timing 로그를 추가할 수 있다. 단, 기본값은 꺼져 있어야 한다.
- 로그를 추가한다면 `DatabaseService.writeCommitted()`와 `ProfitSummaryService.recalculateStoreDateList()`의 소요 시간만 최소한으로 기록한다.

## 하지 말아야 할 것

- 실 DB의 rawPayload를 이 단계에서 바로 prune하지 않는다.
- 수동 매핑 API를 row-level SQL로 바꾸지 않는다.
- UI를 바꾸지 않는다.
- 전체 DB 구조를 바꾸지 않는다.
- performance logging을 기본 활성화하지 않는다.

## 테스트 기준

필수:

- 빈 날짜 목록으로 profit summary refresh를 호출해도 `writeCommitted()`가 실행되지 않는 테스트 추가
- 주문 매핑 대상에 관련 주문상품 날짜가 없을 때 정상 성공하고 추가 summary write가 없는 테스트 추가
- 광고 매핑 대상에 관련 광고 날짜가 없을 때 정상 성공하고 추가 summary write가 없는 테스트 추가
- 기존 backend test 통과
- backend typecheck 통과

명령 예시:

```powershell
npm run test --workspace @patima/backend
npm run typecheck --workspace @patima/backend
```

## 평가자 체크리스트

- 빈 날짜 no-op이 모든 관련 진입점에 적용됐는가
- 날짜 dedupe가 들어갔는가
- 기존 `formatApiSuccess` 응답 스타일을 유지하는가
- best-effort 메서드의 예외 처리 의미가 깨지지 않았는가
- rawPayload 실제 삭제를 하지 않았는가
- 테스트가 실패 없이 통과했는가
