# 0512 프론트 스토어 선택 기능 수정 계획

## 목표

현재 프론트는 대부분의 화면이 `primaryStore` 하나만 기준으로 데이터를 읽는다. 4개 스마트스토어를 모두 등록해도 사용자는 대표 스토어를 바꿔야만 다른 스토어 화면을 볼 수 있다.

1차 목표는 **상단 공통 헤더의 "고정 스토어" 영역을 "선택 스토어" 컨트롤로 바꾸고, 각 페이지가 URL의 `storeId` 값을 읽어 해당 스토어 데이터로 조회/저장/동기화하도록 만드는 것**이다.

이번 작업의 범위는 "스토어별 전환 조회"까지다. 4개 스토어 전체 합산 순이익은 별도 백엔드 합산 API와 UI가 필요하므로 2차 작업으로 남긴다.

## 핵심 설계

### 선택 상태는 URL query로 유지한다

선택된 스토어는 URL query parameter `storeId`로 표현한다.

예시:

```txt
/?storeId=store-a
/orders?storeId=store-a&dateFrom=2026-05-01&dateTo=2026-05-11
/profits?storeId=store-a&date=2026-05-11
/mappings?storeId=store-a
```

이 방식이 필요한 이유:

- Next.js 서버 컴포넌트 페이지가 `searchParams`를 읽어 바로 해당 스토어 데이터를 fetch할 수 있다.
- 사용자가 새로고침하거나 링크를 공유해도 같은 스토어 화면이 열린다.
- `localStorage`만 쓰면 서버 데이터 로딩 함수가 선택값을 모른다.

주의: `app/(main)/layout.tsx`는 page와 달리 `searchParams`를 받지 않는다. 따라서 layout 서버 함수인 `getShellData()`에 직접 선택 storeId를 넘기려 하면 막힌다. 상단 헤더는 클라이언트 컴포넌트이므로 `useSearchParams()`로 현재 URL의 `storeId`를 읽고, `shellData.stores` 목록에서 선택 스토어를 계산한다.

### 공통 선택 로직을 만든다

새 파일을 만든다.

```txt
apps/frontend/lib/store-selection.ts
```

역할:

- `STORE_ID_QUERY_KEY = "storeId"` 상수 제공
- URL/searchParams에서 문자열 하나를 안전하게 읽는 함수 제공
- stores 배열과 requestedStoreId로 현재 스토어를 결정하는 함수 제공
- 현재 query를 보존하면서 storeId만 교체하는 href 생성 함수 제공

권장 코드 형태:

```ts
import type { StoreListItem } from "@/lib/api/types";

export const STORE_ID_QUERY_KEY = "storeId";

export const readSearchParam = (value: string | string[] | undefined) =>
  Array.isArray(value) ? value[0] : value;

export const pickPrimaryStore = (stores: StoreListItem[]) =>
  stores.find((store) => store.isPrimary) ?? stores[0] ?? null;

export const resolveSelectedStore = (
  stores: StoreListItem[],
  requestedStoreId?: string | null,
) => {
  const normalizedStoreId = requestedStoreId?.trim();
  const requestedStore = normalizedStoreId
    ? stores.find((store) => store.id === normalizedStoreId)
    : null;

  return requestedStore ?? pickPrimaryStore(stores);
};

export const buildHrefWithStore = (
  pathname: string,
  currentQuery: URLSearchParams | string | null | undefined,
  storeId: string | null | undefined,
) => {
  const params = new URLSearchParams(
    typeof currentQuery === "string" ? currentQuery : currentQuery?.toString(),
  );

  if (storeId) {
    params.set(STORE_ID_QUERY_KEY, storeId);
  } else {
    params.delete(STORE_ID_QUERY_KEY);
  }

  const query = params.toString();
  return query ? `${pathname}?${query}` : pathname;
};
```

`pickPrimaryStore`는 현재 `apps/frontend/lib/api/services.ts` 안에만 있는데, 여러 곳에서 필요하므로 위 파일로 이동한다. `services.ts`는 이 함수를 import해서 사용한다.

## 데이터 타입 변경

파일:

```txt
apps/frontend/lib/api/types.ts
```

### ShellData

현재:

```ts
export interface ShellData {
  primaryStore: StoreListItem | null;
  storeSource: DataSource;
  today: string;
}
```

수정:

```ts
export interface ShellData {
  stores: StoreListItem[];
  primaryStore: StoreListItem | null;
  storeSource: DataSource;
  today: string;
}
```

`primaryStore`는 기존 호환용으로 유지한다. 헤더에서 실제 표시할 스토어는 `resolveSelectedStore(shellData.stores, searchParams.get("storeId"))`로 계산한다.

### PageData 타입

1차 구현에서는 기존 `primaryStore` 필드를 유지하되, **각 페이지 데이터 함수에서 `primaryStore`에 "실제 선택된 스토어"를 넣는다.**

이렇게 하면 `OrdersView`, `ProfitsView`, `CostsView` 등 기존 컴포넌트의 대규모 rename을 피할 수 있다.

향후 정리 작업에서 `primaryStore` 이름을 `selectedStore` 또는 `currentStore`로 바꾸면 된다. 이번 작업에서 이름까지 모두 바꾸면 수정량이 급격히 늘어난다.

문서/주석에는 다음 정책을 명시한다.

```ts
// In page data objects, primaryStore currently means "active selected store"
// for backward-compatible component props. It falls back to the real primary
// store only when URL storeId is missing or invalid.
```

아래 함수들은 모두 `storeId?: string`을 받도록 바꾼다.


각 함수에서 현재:

```ts

const primaryStore = resolveSelectedStore(storeResponse.data, filtersInput?.storeId);
```


`normalizeOrdersPageFilters`는 `storeId`를 무시하므로 타입만 확장하면 된다.

## 상단 헤더 변경

파일:

```txt
apps/frontend/components/layout/top-header.tsx
```

현재:

- `shellData.primaryStore`를 `store`로 사용한다.
- "고정 스토어" 카드에 이름과 `sellerAccountId / channelNo`를 표시한다.
- store 선택 UI가 없다.

수정:

- `useSearchParams`, `useRouter`를 추가로 import한다.
- `resolveSelectedStore`, `STORE_ID_QUERY_KEY`를 import한다.
- `store`는 `shellData.primaryStore`가 아니라 `resolveSelectedStore(shellData.stores, searchParams.get("storeId"))`로 계산한다.
- "고정 스토어" 라벨을 "선택 스토어"로 바꾼다.
- 카드 내부에 `<select>`를 넣는다.

권장 로직:

```ts
const pathname = usePathname();
const router = useRouter();
const searchParams = useSearchParams();
const selectedStore = resolveSelectedStore(
  shellData.stores,
  searchParams.get(STORE_ID_QUERY_KEY),
);

const handleStoreChange = (nextStoreId: string) => {
  const params = new URLSearchParams(searchParams.toString());
  if (nextStoreId) {
    params.set(STORE_ID_QUERY_KEY, nextStoreId);
  } else {
    params.delete(STORE_ID_QUERY_KEY);
  }
  const query = params.toString();
  router.replace(query ? `${pathname}?${query}` : pathname);
  router.refresh();
};
```

select 예:

```tsx
<select
  className="input-shell mt-2 h-9 text-sm"
  value={selectedStore?.id ?? ""}
  onChange={(event) => handleStoreChange(event.target.value)}
  disabled={shellData.stores.length === 0}
>
  {shellData.stores.map((store) => (
    <option key={store.id} value={store.id}>
      {store.name} {store.isPrimary ? "(대표)" : ""} {store.isActive ? "" : "(비활성)"}
    </option>
  ))}
</select>
```

카드 하단의 `sellerAccountId / channelNo`, 최근 주문 동기화 시간과 상태도 모두 `selectedStore` 기준으로 표시한다.

헤더 우측 액션 링크도 `storeId`를 보존한다.

현재:

```tsx
<Link href="/orders">...</Link>
<Link href="/ads/uploads">...</Link>
```

수정 방향:

```tsx
const selectedStoreId = selectedStore?.id ?? null;
const ordersHref = buildHrefWithStore("/orders", searchParams, selectedStoreId);
const uploadsHref = buildHrefWithStore("/ads/uploads", searchParams, selectedStoreId);
```

그리고 `href={ordersHref}`, `href={uploadsHref}` 사용.

## 사이드바 링크 변경

파일:

```txt
apps/frontend/components/layout/sidebar-nav.tsx
```

현재 사이드바 링크는 `/orders`, `/profits`처럼 고정 href다. 이 상태면 사용자가 스토어를 선택한 뒤 다른 메뉴로 이동할 때 `storeId`가 사라진다.

수정:

- `useSearchParams()` import
- 현재 `storeId`를 읽어서 모든 주요 메뉴 href에 붙인다.
- `/settings/stores`는 storeId가 있어도 문제는 없지만, 설정 화면 내부 선택 UI가 이미 있으므로 붙여도 되고 안 붙여도 된다. 일관성을 위해 붙이는 편이 좋다.

예:

```ts
const searchParams = useSearchParams();
const selectedStoreId = searchParams.get(STORE_ID_QUERY_KEY);
const hrefWithStore = (href: string) =>
  buildHrefWithStore(href, null, selectedStoreId);
```

렌더링:

```tsx
<Link href={hrefWithStore(href)} ...>
```

`active` 계산은 query 없는 pathname 기준으로 유지한다.

## 백엔드 변경 계획

스토어 선택 기능 자체는 기존 백엔드 API를 그대로 사용할 수 있다. 이미 주요 API가 `storeId`를 받는다.

- `POST /api/v1/stores/:storeId/order-sync`
- `GET /api/v1/dashboard/summary?storeId=&date=`
- `GET /api/v1/profits/daily-sales-units?storeId=`
- `GET /api/v1/order-items?storeId=`
- `GET /api/v1/order-source-signatures?storeId=`
- `GET /api/v1/canonical-sales-units?storeId=`
- `POST /api/v1/ad-uploads/preview` body `storeId`
- `GET /api/v1/ad-uploads?storeId=`
- `GET /api/v1/sales-unit-cost-snapshots?storeId=`
- `PUT /api/v1/daily-fake-purchases` body `storeId`
- `GET /api/v1/operations?storeId=`

다만 운영 편의상 **전체 활성 스토어 주문 동기화** 기능은 백엔드에 추가하는 편이 좋다. 사용자가 스토어를 하나씩 선택해서 주문 동기화를 반복하지 않게 하기 위한 기능이다.

### 전체 스토어 순이익 합산은 범위 제외

이번 백엔드 추가 범위는 "전체 활성 스토어의 주문 동기화 작업을 한 번에 enqueue"하는 것이다.

아래는 이번 범위가 아니다.

- 4개 스토어 매출/광고/순이익 합산 API
- 전체 스토어 통합 대시보드
- 스토어 간 판매단위/원가/매핑 복사

### 네이버 24시간 제한 대응

네이버가 한 번의 주문 조회 요청에서 24시간을 초과하는 범위를 거절한다면, 백엔드가 반드시 날짜 단위로 쪼개 요청해야 한다.

현재 구조는 이미 이 정책과 맞는다.

파일:

```txt
apps/backend/src/naver-commerce.service.ts
```

현재 `fetchOrderItems(storeId, dateFrom, dateTo)`는 내부에서 날짜 범위를 일자별로 enumerate하고, 각 날짜마다 `fetchProductOrderIdsByPaymentDate()`를 호출한다. 이 함수는 `targetDateT00:00:00.000+09:00`부터 `targetDateT23:59:59.999+09:00`까지 조회한다.

즉 전체 동기화에서 `2026-05-01 ~ 2026-05-07`을 요청하더라도 실제 네이버 주문 목록 조회는 다음처럼 나뉜다.

```txt
스토어 A / 2026-05-01 00:00~23:59
스토어 A / 2026-05-02 00:00~23:59
...
스토어 B / 2026-05-01 00:00~23:59
스토어 B / 2026-05-02 00:00~23:59
...
```

따라서 전체 동기화 기능에서 별도의 24시간 chunk 로직을 새로 만들 필요는 없다. 기존 `fetchOrderItems`를 그대로 재사용한다.

주의: `helpers.ts`의 `ensureKstDateRange()`는 수동 동기화 범위를 30일로 제한한다. 전체 스토어 동기화도 동일 제한을 사용한다. 4개 스토어 x 30일이면 최소 120개의 날짜별 네이버 목록 조회가 발생한다.

### 왜 백엔드 batch API를 권장하는가

프론트에서 활성 스토어 목록을 돌며 `POST /api/stores/:storeId/order-sync`를 여러 번 호출하는 방식도 가능하다.

하지만 백엔드 batch API가 더 안전하다.

- credential 없는 스토어를 백엔드에서 일관되게 skip할 수 있다.
- 전체 요청의 결과를 한 응답으로 보여줄 수 있다.
- 같은 스토어에 이미 동기화 작업이 있으면 skip 또는 queue 정책을 백엔드에서 통제할 수 있다.
- 추후 전체 동기화 audit log나 rate limit 대응을 붙이기 쉽다.

## OrderSyncService 수정

### 1. performSync에 requireLiveCredential 옵션 추가

현재 단일 주문 동기화는 credential이 없으면 mock fallback 주문을 생성한다.

전체 스토어 동기화에서 이 동작은 위험하다. 신규 스토어 credential이 아직 없는데 전체 동기화 버튼을 누르면 가짜 주문 데이터가 들어갈 수 있기 때문이다.

따라서 `performSync`에 옵션을 추가한다.

```ts
async performSync(
  storeId: string,
  dateFrom: string,
  dateTo: string,
  rangeMode: "MANUAL" | "AUTO_LAST_30_DAYS",
  options?: { requireLiveCredential?: boolean },
) {
  ...
  const resolvedConfiguration = this.naverCommerceService.getResolvedConfiguration(storeId);
  const liveEnabled = !!resolvedConfiguration;

  if (options?.requireLiveCredential && !liveEnabled) {
    throw new BadRequestException("NAVER_CREDENTIALS_NOT_CONFIGURED");
  }

  const liveEntries = liveEnabled
    ? await this.naverCommerceService.fetchOrderItems(storeId, dateFrom, dateTo)
    : null;
  ...
}
```

단일 스토어 기존 API는 지금처럼 fallback 동작을 유지해도 된다. 전체 스토어 동기화로 생성되는 operation만 `requireLiveCredential: true`를 사용한다.

### 2. retry executor가 requireLiveCredential을 보존하게 수정

현재 retry executor는 `requestJson`에서 날짜와 rangeMode만 읽는다.

수정:

```ts
this.operationService.registerRetryExecutor("ORDER_SYNC", async (operation) => {
  const request = operation.requestJson as {
    dateFrom: string;
    dateTo: string;
    rangeMode: string;
    requireLiveCredential?: boolean;
  };

  return this.performSync(
    operation.storeId,
    request.dateFrom,
    request.dateTo,
    request.rangeMode as "MANUAL" | "AUTO_LAST_30_DAYS",
    { requireLiveCredential: request.requireLiveCredential === true },
  );
});
```

### 3. enqueueSyncAll 메서드 추가

새 메서드:

```ts
enqueueSyncAll(dateFrom?: string, dateTo?: string) {
  const { dateFrom: normalizedDateFrom, dateTo: normalizedDateTo, rangeMode } =
    ensureKstDateRange(dateFrom, dateTo);

  const snapshot = this.databaseService.getSnapshot();
  const activeStores = snapshot.stores.filter((store) => store.isActive);

  const operations = [];
  const skippedStores = [];

  for (const store of activeStores) {
    if (this.operationService.hasInFlightOperation?.(store.id, "ORDER_SYNC")) {
      skippedStores.push({
        storeId: store.id,
        storeName: store.name,
        reason: "ORDER_SYNC_ALREADY_IN_FLIGHT",
      });
      continue;
    }

    if (!this.naverCommerceService.getResolvedConfiguration(store.id)) {
      skippedStores.push({
        storeId: store.id,
        storeName: store.name,
        reason: "NAVER_CREDENTIALS_NOT_CONFIGURED",
      });
      continue;
    }

    const operation = this.operationService.enqueue(
      store.id,
      "ORDER_SYNC",
      {
        dateFrom: normalizedDateFrom,
        dateTo: normalizedDateTo,
        rangeMode,
        requireLiveCredential: true,
        requestedByBatch: true,
      },
      () =>
        this.performSync(
          store.id,
          normalizedDateFrom,
          normalizedDateTo,
          rangeMode,
          { requireLiveCredential: true },
        ),
    );

    operations.push({
      storeId: store.id,
      storeName: store.name,
      operationId: operation.id,
      operationType: operation.operationType,
      status: operation.status,
    });
  }

  if (operations.length === 0 && skippedStores.length === 0) {
    throw new BadRequestException({
      success: false,
      message: "활성 스토어가 없습니다.",
      errors: [{ field: "storeId", reason: "NO_ACTIVE_STORES" }],
    });
  }

  return formatApiSuccess({
    dateFrom: normalizedDateFrom,
    dateTo: normalizedDateTo,
    rangeMode,
    targetStoreCount: operations.length,
    skippedStoreCount: skippedStores.length,
    operations,
    skippedStores,
  });
}
```

위 예시의 `hasInFlightOperation?.`는 새로 추가할 OperationService 메서드를 전제로 한다. 실제 구현 시 optional chaining은 쓰지 말고 정식 메서드를 추가한다.

## OperationService 수정

파일:

```txt
apps/backend/src/operation.service.ts
```

현재는 `hasRunningOperation(storeId)`만 있다. 전체 동기화 버튼은 같은 스토어에 이미 주문 동기화가 `QUEUED` 또는 `RUNNING` 상태일 때 중복 enqueue를 피하는 것이 좋다.

새 메서드를 추가한다.

```ts
hasInFlightOperation(storeId: string, operationType?: OperationType): boolean {
  this.cleanupStaleOperations();
  const snapshot = this.databaseService.getSnapshot();
  return snapshot.operations.some(
    (operation) =>
      operation.storeId === storeId &&
      (operation.status === "QUEUED" || operation.status === "RUNNING") &&
      (!operationType || operation.operationType === operationType),
  );
}
```

기존 `hasRunningOperation`은 유지한다. 다른 서비스의 동작이 바뀌지 않도록 한다.

## 주의할 점

- `layout.tsx`에서 선택 storeId를 서버로 받으려 하지 말 것. layout은 `searchParams`를 받지 않는다.
- `TopHeader`는 클라이언트에서 URL query를 읽어 표시만 담당한다.
- 실제 데이터 fetch 기준은 각 page 서버 컴포넌트가 `searchParams.storeId`를 읽어 `get*PageData({ storeId })`로 넘기는 것이다.
- URL의 `storeId`가 존재하지 않거나 잘못된 값이면 `resolveSelectedStore`가 대표 스토어 또는 첫 스토어로 fallback해야 한다.
- inactive store도 목록에는 표시한다. 조회는 가능하게 두되, 쓰기성 작업은 기존 백엔드 `STORE_INACTIVE` 검증에 맡긴다.
- 이번 작업에서 `primaryStore` prop 이름을 전부 바꾸려 하면 수정 범위가 커진다. 1차에서는 "선택 스토어를 primaryStore 필드에 담는 호환 방식"으로 간다.
- 2차 전체 합산 기능은 별도다. 이 작업으로는 각 스토어별 전환 조회만 가능하다.

## 완료 기준

- 상단 헤더에서 스토어를 선택할 수 있다.
- 선택하면 URL에 `storeId`가 반영된다.
- 대시보드/주문/판매단위/매핑/광고 업로드/원가/손익/작업 이력 페이지가 모두 선택 스토어 기준 데이터를 읽는다.
- 사이드바 이동, 필터 변경, 날짜 변경 후에도 선택 스토어가 유지된다.
- 주문 동기화, 광고 업로드, 원가 업로드, 가구매 저장 같은 쓰기 작업도 선택 스토어 ID를 사용한다.
- `npm run lint` 또는 최소 프론트 typecheck가 통과한다.
