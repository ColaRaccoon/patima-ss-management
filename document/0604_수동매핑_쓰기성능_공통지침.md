# 0604 수동 매핑 쓰기 성능 개선 - 공통 지침

모든 단계 작업자는 이 파일을 먼저 읽고, 이후 해당 단계 파일을 읽어야 한다.

## 공통 시작 규칙

새 세션에서 단계 파일을 받으면 메인 작업자는 다음 절차를 따른다.

1. `tool_search`에서 `sub-agent`, `agent`, `multi-agent`, `thread`, `create_thread`, `send_message_to_thread`, `read_thread` 같은 키워드로 사용 가능한 서브 에이전트 또는 백그라운드 스레드 도구를 찾는다.
2. 사용 가능한 도구로 서브 에이전트 2개를 만든다.
   - 개발자 에이전트: 현재 단계 구현 담당
   - 평가자 에이전트: 개발 결과 검토 담당
3. 개발자 에이전트에게 현재 단계 파일과 이 공통 지침의 핵심 내용을 전달한다.
4. 개발자 에이전트가 구현을 끝내면 평가자 에이전트에게 전체 diff와 테스트 결과를 전달한다.
5. 평가자 에이전트는 결함을 하나라도 발견하면 `REWORK REQUIRED` 또는 `재작업 필요`라고 판정하고 구체적 수정 지시를 남긴다.
6. 메인 작업자는 개발자 에이전트에게 재작업을 지시한다.
7. 개발자 재작업 후 평가자 재검토를 반복한다.
8. 평가자 에이전트가 명시적으로 `ACCEPTED` 또는 `합격`이라고 판정하고, 메인 작업자가 직접 diff와 테스트 결과를 확인한 뒤에만 완료한다.

서브 에이전트 도구가 실제로 제공되지 않는 환경이면 작업자는 시작 전에 사용자에게 도구 부재를 보고해야 한다. 이 계획은 서브 에이전트 방식 사용을 전제로 한다.

## 평가자 공통 체크리스트

평가자 에이전트는 모든 단계에서 아래 항목을 검토한다.

- 단계 파일의 목표와 구현 결과가 일치하는가
- 단계 범위를 넘어선 불필요한 수정이 없는가
- 기존에 재활용 가능한 함수, helper, service, query builder가 있는데 새로 중복 구현하지 않았는가
- 기존 코드 스타일, Nest service/controller 패턴, TypeScript 타입 스타일에서 벗어나지 않았는가
- PostgreSQL mode와 file mode fallback을 모두 고려했는가
- 기존 집/회사 DB 동기화 도구, export/import, rawPayload 보존 정책을 깨지 않았는가
- 테스트가 충분하고 실제로 통과했는가
- 프로그램이 빌드/타입체크/테스트에서 실패하지 않는가
- 성능 개선 목적과 무관한 UI/기능 변경이 섞이지 않았는가
- 위험한 명령, 임의 데이터 삭제, 승인 없는 실 DB 변경이 없는가

## 현재 구조와 병목 요약

현재 앱은 PostgreSQL을 사용하지만, 쓰기 구조는 정규화된 row-level 업데이트라기보다 `DatabaseShape` 메모리 snapshot을 중심으로 동작한다.

핵심 병목:

1. 서버 시작 시 PostgreSQL의 `id + payload JSONB` 테이블들을 모두 읽어 메모리 `DatabaseShape`로 만든다.
2. 대부분의 쓰기 API는 `DatabaseService.writeCommitted()`를 호출한다.
3. `writeCommitted()`는 전체 `DatabaseShape`를 `JSON.parse(JSON.stringify(...))`로 deep clone한다.
4. PostgreSQL 저장 시 `persistSnapshotToPostgres()`가 모든 storage table을 순회한다.
5. 각 row를 JSON 직렬화하고 `payload_hash`를 계산한 뒤 upsert batch를 만든다.
6. 변경되지 않은 row는 최종 UPDATE를 피하지만, 그 전 단계의 전체 순회/직렬화/hash/query 비용은 여전히 발생한다.
7. 수동 매핑 저장 후 순이익 요약 재계산이 추가 `writeCommitted()`를 호출한다.

실제 DB 규모 예시:

- `order_items`: 34,133 rows, payload 약 104MB
- `orders`: 25,644 rows, payload 약 69MB
- 백업 snapshot: 약 440MB
- `orders.rawPayload`, `order_items.rawPayload` 대부분이 아직 non-null

## 기존 최적화와 이번 계획의 관계

기존 Git 이력에는 다음 개선이 이미 있다.

- 주문/광고 목록 서버 페이지네이션
- PostgreSQL query branch와 JSONB expression index
- runtime persistence의 `TRUNCATE + 전체 재삽입` 제거
- `payload_hash` 기반 변경 row update 회피
- rawPayload 보존/정리 스크립트
- 손익 페이지 SSR timeout 완화

하지만 수동 매핑 저장 hot path는 아직 완전히 해결되지 않았다.

이번 계획은 기존 작업을 버리는 것이 아니라, 그 위에 다음 범위를 추가한다.

- 수동 매핑 저장에서 전체 snapshot clone/persistence를 타지 않도록 한다.
- 순이익 요약 갱신도 해당 날짜 row만 교체하도록 한다.
- 주문/광고 수동 매핑, 의도적 제외, 자동 재계산 같은 자주 누르는 쓰기 버튼을 부분 SQL 업데이트로 분리한다.

## PostgreSQL direct write 원칙

PostgreSQL direct write를 추가할 때는 다음을 지킨다.

1. transaction을 사용한다.
2. 대상 row만 조회한다.
3. payload를 기존 TypeScript 타입에 맞춰 mutate한다.
4. `payload_hash`를 반드시 갱신한다.
5. DB commit 후 메모리 snapshot을 같은 내용으로 갱신한다.
6. file mode fallback을 유지한다.
7. 기존 `writeCommitted()`를 완전히 제거하려고 하지 말고, hot path부터 분리한다.

## 메모리 snapshot 갱신 원칙

PostgreSQL direct write 후 메모리 snapshot 갱신을 빠뜨리면 다음 API 응답이 오래된 데이터를 반환할 수 있다.

따라서 direct write 메서드는 다음 중 하나를 반드시 수행한다.

- DB transaction 안에서 읽고 mutate한 payload를 commit 후 해당 in-memory 배열에도 반영
- 또는 transaction 후 해당 row만 재조회해 memory에 upsert

전체 `loadSnapshotFromPostgres()` 재호출은 성능 목적에 어긋나므로 사용하지 않는다.

## 테스트 작성 원칙

테스트는 과하게 넓히지 않되, hot path는 반드시 검증한다.

필수 관점:

- PostgreSQL mode direct path
- file mode fallback
- 메모리 snapshot consistency
- cross-store 방어
- inactive/group sales unit validation
- affected dates 정확성
- 기존 비즈니스 규칙 유지

## 승인 필요한 작업

다음 작업은 사용자 승인 없이 실행하지 않는다.

- 실 DB에 수동 매핑 POST 요청
- `prune-order-raw-payloads.mjs --yes`
- `db-import.mjs --yes`
- 데이터 삭제/초기화
- destructive git 명령

읽기 전용 작업은 승인 없이 가능하다.

- `node scripts/report-db-size.mjs`
- health check
- GET API 측정
- 테스트 fixture 기반 성능 측정

## 최종 목표 상태

모든 단계가 끝나면 다음 상태가 되어야 한다.

1. 수동 주문 매핑 저장은 대상 signature/order item만 갱신한다.
2. 수동 광고 매핑 저장은 대상 signature/ad cost row만 갱신한다.
3. 순이익 요약은 영향 날짜의 daily summary row만 교체한다.
4. PostgreSQL mode에서 수동 매핑 저장이 전체 `DatabaseShape` clone과 전체 table persistence를 타지 않는다.
5. file mode fallback은 계속 동작한다.
6. 기존 export/import 기반 집/회사 DB 동기화는 유지된다.
7. rawPayload 정리 절차가 문서화되어 운영자가 DB 크기를 관리할 수 있다.
8. 테스트와 문서가 새 구조를 뒷받침한다.
