# 0617 수정계획 - order_items 상품명/옵션명/시그니처 반복 저장 정규화

## 목적

이번 작업의 목적은 `order_items` payload에 모든 주문상품 row마다 반복 저장되는 상품명, 옵션명, 정규화 텍스트, 시그니처 문자열을 줄이고, 이미 존재하는 `order_source_signatures`를 주문상품 원문 표시/검색/매핑 기준 테이블처럼 활용하도록 데이터 흐름을 정리하는 것이다.

0616 작업에서 `orders`, `order_items`의 네이버 원본 JSON인 `rawPayload`는 이미 `null` 처리했고, 새 주문 동기화도 기본적으로 rawPayload 객체를 만들지 않도록 바꿨다. 그 결과 가장 큰 원본 JSON 덩어리는 제거되었다. 이제 남은 가장 큰 반복 저장 영역은 `order_items` 내부의 아래 필드들이다.

- `rawProductName`
- `rawOptionInfo`
- `normalizedProductName`
- `normalizedOptionInfo`
- `sourceSignature`

이 필드들은 주문상품마다 저장되어 있지만, 사실상 같은 상품명/옵션명 조합별로 만들어지는 `order_source_signatures`에도 같은 정보가 이미 저장된다.

- `order_source_signatures.rawProductNameSnapshot`
- `order_source_signatures.rawOptionInfoSnapshot`
- `order_source_signatures.normalizedProductName`
- `order_source_signatures.normalizedOptionInfo`
- `order_source_signatures.sourceSignature`

따라서 주문상품 row는 `orderSourceSignatureId`만 들고 있고, 원문 상품명/옵션명/시그니처가 필요할 때 `order_source_signatures`를 join하거나 메모리 snapshot에서 lookup해 보강하는 구조로 바꿀 수 있다.

## 현재 측정값

2026-06-16 rawPayload 제거 후 현재 PostgreSQL 측정값:

```text

전체 JSONB payload: 90,241,396 bytes
전체 JSON text/export payload: 73,942,010 bytes
PostgreSQL relation total: 160,112,640 bytes
```

테이블별 주요 payload:

```text
order_items: 40,992 rows, 69,314,109 bytes
orders: 31,658 rows, 13,124,463 bytes
ad_campaign_daily_costs: 4,275 rows, 4,138,305 bytes
```

`order_items`가 전체 JSONB payload의 약 76.8%를 차지한다.

`order_items` 내부 반복 필드별 value 크기:

| 필드 | rows | value bytes |
| --- | ---: | ---: |
| `sourceSignature` | 40,992 | 8,171,566 |
| `rawProductName` | 40,992 | 4,949,420 |
| `normalizedProductName` | 40,992 | 4,948,796 |
| `normalizedOptionInfo` | 40,992 | 3,398,705 |
| `rawOptionInfo` | 40,992 | 3,398,705 |

시나리오별 예상 절감:

| 시나리오 | order_items JSONB 절감 | order_items 절감률 | 전체 JSONB 절감률 | 전체 JSON text/export 절감률 |
| --- | ---: | ---: | ---: | ---: |
| 1단계: `normalizedProductName`, `normalizedOptionInfo`, `sourceSignature` 제거 | 18,238,359 bytes | 26.31% | 약 20.2% | 약 13.3% |

권장 목표는 2단계까지다. 다만 기능 영향 범위가 있으므로 구현은 안전하게 1단계와 2단계로 나누어 검증 가능하게 진행한다.

### `OrderSourceSignature`

파일: `packages/shared/src/types.ts`

`OrderSourceSignature`는 이미 상품명/옵션명 조합별 snapshot과 정규화 값을 가진다.

```ts
export interface OrderSourceSignature {
  id: string;
  storeId: string;
  sourceSignature: string;
  rawProductNameSnapshot: string;
  rawOptionInfoSnapshot: string | null;
  normalizedProductName: string;
  normalizedOptionInfo: string;

  mappingStatus: MappingStatus;
  confirmedAt: string | null;
  usageCount: number;
  // ...

```

현재 `order_items.orderSourceSignatureId`가 `order_source_signatures.id`를 가리키므로, 주문상품 표시/검색에 필요한 원문 값은 signature에서 얻을 수 있다.

## 현재 코드 흐름

### 1. 주문 동기화

파일: `apps/backend/src/order-sync.service.ts`

핵심 위치:

- `performSync()`
- `upsertSignature()`
- `updateSignatureUsageSummary()`
- `upsertProduct()`
- `generateMockItems()`

현재 흐름:

1. 네이버 주문 상세를 `SyncedOrderItemInput`으로 파싱한다.
2. `upsertProduct()`가 `entry.rawProductName`을 `products.productName`에 저장한다.
3. `upsertSignature()`가 `entry.rawProductName`, `entry.rawOptionInfo`를 기준으로 `order_source_signatures`를 생성/갱신한다.
4. `OrderItem` payload를 만들 때 같은 원문/정규화/시그니처 필드를 다시 저장한다.

현재 중복 저장 부분:

```ts
const payload: OrderItem = {
  // ...
  orderSourceSignatureId: signature.id,
  rawProductName: entry.rawProductName,
  rawOptionInfo: entry.rawOptionInfo,
  normalizedProductName: normalizeText(entry.rawProductName),
  normalizedOptionInfo: normalizeText(entry.rawOptionInfo ?? ""),
  sourceSignature: rawToSourceSignature(entry.rawProductName, entry.rawOptionInfo),
  // ...
};
```

변경 방향:

- `upsertSignature()`는 유지한다. 이 함수가 정규화 후 기준 row를 만드는 핵심 재활용 지점이다.
- `OrderItem`에는 장기적으로 `rawProductName`, `rawOptionInfo`, `normalizedProductName`, `normalizedOptionInfo`, `sourceSignature`를 저장하지 않는다.
- 주문 목록/검색/매핑에서 필요한 값은 `orderSourceSignatureId`로 signature를 찾아 사용한다.

### 2. 주문 목록 조회

파일:

- `apps/backend/src/order-sync.service.ts`
- `apps/backend/src/database.service.ts`
- `apps/backend/src/helpers.ts`

현재 `OrderSyncService.listOrderItems()`는 `DatabaseService.queryOrderItems()`로 `OrderItem[]`을 받은 뒤 `mapOrderItemResponse(snapshot, item)`으로 API 응답을 만든다.

```ts
const snapshot = this.databaseService.getSnapshot();
const result = await this.databaseService.queryOrderItems(query);
return formatApiSuccess({
  ...result,
  items: result.items.map((item) => mapOrderItemResponse(snapshot, item)),
});
```

PostgreSQL mode의 `DatabaseService.queryOrderItems()`는 이미 `order_source_signatures`를 LEFT JOIN하고 있다.

```sql
FROM order_items items
LEFT JOIN order_source_signatures signatures
  ON signatures.id = items.payload->>'orderSourceSignatureId'
```

하지만 현재 상품명/옵션명 검색은 `items.payload` 안의 정규화 필드를 본다.

```ts
COALESCE(items.payload->>'normalizedProductName', '') LIKE ...
COALESCE(items.payload->>'normalizedOptionInfo', '') LIKE ...
```

변경 방향:

- PostgreSQL query는 이미 있는 `signatures` join을 재활용한다.
- 상품명 검색은 `signatures.payload->>'normalizedProductName'` 기준으로 바꾼다.
- 옵션명 검색은 `signatures.payload->>'normalizedOptionInfo'` 기준으로 바꾼다.
- 응답 표시값도 `item.rawProductName`이 아니라 signature snapshot에서 보강한다.

권장 SQL:

```ts
builder.addCondition(
  "COALESCE(signatures.payload->>'normalizedProductName', '') LIKE {param} ESCAPE '\\'",
  likePattern(keywordProduct),
);

builder.addCondition(
  "COALESCE(signatures.payload->>'normalizedOptionInfo', '') LIKE {param} ESCAPE '\\'",
  likePattern(keywordOption),
);
```

`mapOrderItemResponse()`는 signature lookup을 사용하도록 바꾼다.

권장 헬퍼:

```ts
export const resolveOrderItemSignatureDisplay = (
  database: DatabaseShape,
  item: Pick<OrderItem, "orderSourceSignatureId">,
) => {
  const signature = item.orderSourceSignatureId
    ? database.orderSourceSignatures.find((entry) => entry.id === item.orderSourceSignatureId)
    : null;

  return {
    rawProductName: signature?.rawProductNameSnapshot ?? "",
    rawOptionInfo: signature?.rawOptionInfoSnapshot ?? null,
    sourceSignature: signature?.sourceSignature ?? "",
    normalizedProductName: signature?.normalizedProductName ?? "",
    normalizedOptionInfo: signature?.normalizedOptionInfo ?? "",
  };
};
```

단, 전환 중 호환성을 위해 기존 item 필드가 남아 있을 수도 있으므로 초기 구현에서는 fallback을 둔다.

```ts
rawProductName: signature?.rawProductNameSnapshot ?? item.rawProductName ?? "",
rawOptionInfo: signature?.rawOptionInfoSnapshot ?? item.rawOptionInfo ?? null,
sourceSignature: signature?.sourceSignature ?? item.sourceSignature ?? "",
```

### 3. file mode / snapshot mode 조회

파일: `apps/backend/src/database.service.ts`

`queryOrderItemsFromSnapshot()`는 현재 `item.normalizedProductName`, `item.normalizedOptionInfo`를 직접 사용한다.

```ts
.filter((item) => (keywordProduct ? item.normalizedProductName.includes(keywordProduct) : true))
.filter((item) => (keywordOption ? item.normalizedOptionInfo.includes(keywordOption) : true))
```

변경 방향:

- snapshot mode에서도 `orderSourceSignatureId`로 signature를 찾아 검색한다.
- fallback으로 기존 item 필드를 잠시 허용한다.

권장 helper:

```ts
private getOrderItemSignature(item: OrderItem): OrderSourceSignature | null {
  return item.orderSourceSignatureId
    ? this.database.orderSourceSignatures.find((signature) => signature.id === item.orderSourceSignatureId) ?? null
    : null;
}
```

또는 `helpers.ts`의 공용 lookup helper를 써도 된다.

### 4. 주문 수동 매핑 저장

파일: `apps/backend/src/database.service.ts`

`saveOrderManualMappingsCommitted()`는 signature와 관련 item을 함께 업데이트한다.

현재 구조:

- `order_source_signatures` row를 업데이트한다.
- 관련 `order_items` row의 `canonicalSalesUnitId`, `updatedAt` 등을 업데이트한다.

이 흐름은 유지한다. 이번 정규화의 핵심은 item payload에서 표시/검색 중복 필드를 제거하는 것이며, item의 `orderSourceSignatureId`, `canonicalSalesUnitId`, 매출/수수료/배송비/날짜 필드는 유지해야 한다.

주의:

- 수동 매핑 API는 signature id를 기준으로 동작한다.
- `order_items.orderSourceSignatureId`를 제거하면 안 된다.
- `saveOrderManualMappingsCommitted()`의 row-level direct update 성능 최적화는 유지해야 한다.

### 5. 자동 주문 매핑

파일: `apps/backend/src/sales-unit-auto-mapper.ts`

현재 자동매핑은 크게 두 축이다.

1. `OrderSourceSignature` 기반 텍스트 매칭
2. `OrderItem` 기반 ID 매칭

텍스트 매칭은 이미 signature를 사용한다.

```ts
const buildOrderLookupValues = (signature: OrderSourceSignature): string[] =>
  dedupe([
    normalizeMatchAlias(signature.normalizedProductName),
    normalizeMatchAlias(signature.normalizedOptionInfo),
    normalizeMatchAlias(signature.sourceSignature),
    normalizeMatchAlias(`${signature.normalizedProductName} ${signature.normalizedOptionInfo}`),
  ]);
```

ID 매칭 중 함께배송 여부 판별은 현재 `item.rawOptionInfo`를 본다.

```ts
const isBundledItem = item.rawOptionInfo?.includes("[함께배송") ?? false;
```

변경 방향:

- `item.rawOptionInfo` 대신 signature snapshot의 `rawOptionInfoSnapshot`을 사용한다.
- 이미 `signaturesById` map이 있으므로 추가 lookup 비용은 거의 없다.

권장 변경:

```ts
const rawOptionInfo = signature?.rawOptionInfoSnapshot ?? item.rawOptionInfo ?? null;
const isBundledItem = rawOptionInfo?.includes("[함께배송") ?? false;
```

완전 정규화 후에는 fallback의 `item.rawOptionInfo`를 제거한다.

### 6. 시그니처 표시명 보강

파일: `apps/backend/src/signature-enrichment.ts`

현재 보강 순서 중 `order_items.rawProductName`, `order_items.rawOptionInfo` fallback이 있다.

```ts
// Step 2: Check order_items rawProductName
// Step 3: Also try order_items rawOptionInfo
```

변경 방향:

- `OrderSourceSignature`가 원문 snapshot의 단일 기준이 되므로, 이 fallback의 중요도는 낮아진다.
- 다만 기존 sparse signature 보정 때문에 남겨두려면 item 필드 optional fallback으로만 둔다.
- 완전 정규화 후에는 아래 대체 순서를 권장한다.

권장 순서:

1. `signature.rawProductNameSnapshot`
2. `signature.rawOptionInfoSnapshot`에서 패턴 추출
3. `products.productName` via `sampleExternalProductId`
4. 과거 호환 fallback으로만 `orderItems`의 raw 필드 확인

`scripts/diagnostics/inspect-sparse-signatures.mjs`도 같은 방향으로 수정하거나, 진단 스크립트는 legacy 진단용이라고 명시한다.

### 7. 초기 매핑 seed

파일: `apps/backend/src/mapping-seed.service.ts`

현재 `MappingSeedService`는 `orderItems`의 원문 필드를 직접 사용한다.

주요 사용:

- `parseShippedTogetherOption(item.rawOptionInfo)`

변경 방향:

권장 helper:

```ts
const signaturesById = new Map(
  draft.orderSourceSignatures.map((signature) => [signature.id, signature]),

const getOrderItemRawText = (item: OrderItem) => {
  const signature = item.orderSourceSignatureId
    ? signaturesById.get(item.orderSourceSignatureId)
    : null;
  return {
    rawProductName: signature?.rawProductNameSnapshot ?? item.rawProductName ?? "",
    rawOptionInfo: signature?.rawOptionInfoSnapshot ?? item.rawOptionInfo ?? null,
```

## 권장 구현 전략

### 1단계 - 안전한 read-path 전환

목표:

- DB에는 아직 기존 중복 필드가 있어도 된다.
- 모든 조회/검색/매핑 로직이 먼저 `order_source_signatures`를 기준으로 동작하도록 바꾼다.
- fallback으로 기존 item 필드를 허용한다.

수정 대상:

```text
apps/backend/src/helpers.ts
apps/backend/src/database.service.ts
apps/backend/src/sales-unit-auto-mapper.ts
apps/backend/src/mapping-seed.service.ts
apps/backend/src/signature-enrichment.ts
apps/backend/src/run-tests.ts
```

필수 변경:

- `mapOrderItemResponse()`가 signature lookup 기반으로 상품명/옵션명/시그니처를 반환한다.
- `DatabaseService.queryOrderItems()`의 PostgreSQL 검색 조건이 `signatures.payload`의 normalized fields를 본다.
- `queryOrderItemsFromSnapshot()`도 signature lookup 기반 검색을 한다.
- `sales-unit-auto-mapper.ts`의 함께배송 판별이 signature raw option을 본다.
- `mapping-seed.service.ts`의 raw product/option 사용을 signature 기반 helper로 바꾼다.
- `signature-enrichment.ts`는 item raw field 의존을 fallback으로 낮춘다.

검증:

- 기존 DB에서 중복 필드가 아직 남아 있는 상태로 backend test 통과.
- 주문 목록 날짜/상품명/옵션명/mappingStatus/orderStatus/saleStatus/paymentDateStatus 필터 동작.
- 수동 매핑 저장과 자동 매핑 재계산 동작.
- 마진/일별 손익 조회 동작.

### 2단계 - write-path 중복 저장 중단

목표:

- 새 주문 동기화부터 `OrderItem`에 중복 필드를 쓰지 않는다.
- 저장 타입은 transition을 위해 optional 허용으로 바꾼다.

수정 대상:

```text
packages/shared/src/types.ts
apps/backend/src/order-sync.service.ts
apps/backend/src/database.service.ts
apps/backend/src/helpers.ts
apps/backend/src/run-tests.ts
apps/frontend/lib/api/types.ts
```

권장 타입 변경:

```ts
export interface OrderItem {
  // ...
  rawProductName?: string;
  rawOptionInfo?: string | null;
  normalizedProductName?: string;
  normalizedOptionInfo?: string;
  sourceSignature?: string;
  // ...
}
```

주의:

- 바로 타입에서 필드를 완전 삭제하지 말고 optional로 먼저 낮춘다.
- 기존 fixture/test가 많으므로 optional 전환 후 각 로직이 signature fallback을 사용하도록 고친다.
- API 응답 타입은 유지한다.

`OrderSyncService.performSync()` 변경:

```ts
const payload: OrderItem = {
  id: existingItem?.id ?? createId(),
  orderId: orderRecord.id,
  storeId,
  productId: product.id,
  orderSourceSignatureId: signature.id,
  canonicalSalesUnitId: null,
  externalProductOrderId: entry.externalProductOrderId,
  externalProductId: product.externalProductId,
  optionCode: entry.optionCode,
  packageNumber: entry.packageNumber,
  // rawProductName/rawOptionInfo/normalizedProductName/normalizedOptionInfo/sourceSignature 저장 중단
  quantity: entry.quantity,
  // ...
};
```

단, `existingItem` 업데이트 시 과거 필드가 남아 있으면 Object.assign만으로는 필드가 삭제되지 않는다. 새 write-path에서 중복 필드를 제거하려면 명시적으로 delete해야 한다.

```ts
delete (payload as Partial<OrderItem>).rawProductName;
delete (payload as Partial<OrderItem>).rawOptionInfo;
delete (payload as Partial<OrderItem>).normalizedProductName;
delete (payload as Partial<OrderItem>).normalizedOptionInfo;
delete (payload as Partial<OrderItem>).sourceSignature;
```

더 권장하는 방식은 payload 생성 helper를 만들고, 저장 직전 `stripOrderItemRepeatedTextFields()`를 적용하는 것이다.

```ts
const stripOrderItemRepeatedTextFields = (item: OrderItem): OrderItem => {
  const next = { ...item };
  delete (next as Partial<OrderItem>).rawProductName;
  delete (next as Partial<OrderItem>).rawOptionInfo;
  delete (next as Partial<OrderItem>).normalizedProductName;
  delete (next as Partial<OrderItem>).normalizedOptionInfo;
  delete (next as Partial<OrderItem>).sourceSignature;
  return next;
};
```

### 3단계 - 기존 DB 마이그레이션

목표:

- 기존 `order_items.payload`에서 중복 필드를 제거한다.
- row는 삭제하지 않는다.
- `orderSourceSignatureId`, 금액, 수수료, 배송비, 날짜, mapping 관련 필드는 유지한다.

### 4단계 - 물리 공간 회수

마이그레이션은 JSONB payload 논리 크기를 줄인다. PostgreSQL relation 파일 크기는 즉시 줄지 않을 수 있다.

클라우드 DB 업로드 목적이면 보통 아래 흐름이 더 낫다.

```powershell
node scripts/db-export.mjs
node scripts/db-import.mjs backups/patima-xxxx.json --yes
```

클라우드에 새로 import하면 row가 새 payload로 적재되어 local UPDATE dead space를 같이 가져가지 않는다.

로컬 DB 파일 자체를 줄여야 한다면 별도 승인 후:

```sql
VACUUM FULL ANALYZE order_items;
REINDEX TABLE order_items;
```

주의:

- `VACUUM FULL`은 exclusive lock을 건다.
- backend를 중지하고 실행한다.
- 사용자가 명시적으로 승인한 경우에만 실행한다.

## 리스크와 대응

### 리스크 1. 주문 목록 검색이 깨질 수 있음

원인:

- 기존 검색이 `order_items.payload->>'normalizedProductName'`를 직접 봄.

대응:

- PostgreSQL query에서 이미 join 중인 `order_source_signatures`의 normalized fields를 사용한다.
- snapshot mode도 signature lookup 기반으로 바꾼다.
- 테스트를 추가한다.

### 리스크 2. 화면 표시값이 빈 값이 될 수 있음

원인:

- `mapOrderItemResponse()`가 `item.rawProductName`을 직접 반환함.

대응:

- `mapOrderItemResponse()`에서 signature snapshot을 우선 사용한다.
- fallback으로 item legacy fields를 둔다.
- signature가 없거나 깨진 item은 빈 문자열 또는 `externalProductOrderId` 기반 fallback을 반환하고, 진단 가능하게 한다.

### 리스크 3. 자동매핑 함께배송 판별이 바뀔 수 있음

원인:

- 현재 함께배송 판별이 `item.rawOptionInfo`에 의존함.

대응:

- `signaturesById`에서 signature를 이미 찾고 있으므로 `signature.rawOptionInfoSnapshot`을 사용한다.
- fallback으로 legacy item rawOptionInfo를 둔다.

### 리스크 4. 수동 매핑 direct update가 중복 필드를 다시 저장할 수 있음

원인:

- `saveOrderManualMappingsCommitted()`는 기존 item payload를 clone해서 업데이트한다.
- 기존 payload에 중복 필드가 있으면 그대로 보존될 수 있다.

대응:

- 마이그레이션 후에는 필드가 없으므로 새로 생기지 않는지 테스트한다.
- direct update 경로에서 `stripOrderItemRepeatedTextFields()`를 적용할지 검토한다.
- 최소한 `OrderSyncService` write-path에서는 중복 필드가 다시 생기지 않게 한다.

### 리스크 5. 기존 sparse signature 보정 로직이 약해질 수 있음

원인:

- `signature-enrichment.ts`가 item raw fields를 fallback으로 사용함.

대응:

- 정규화 전에 모든 `order_items`가 valid `orderSourceSignatureId`를 갖고 있고, signature snapshot이 비어 있지 않은지 진단한다.
- 비어 있는 signature는 마이그레이션 전에 legacy item raw fields로 backfill한다.

진단 SQL:

```sql
SELECT COUNT(*) AS missing_signature_count
FROM order_items items
LEFT JOIN order_source_signatures signatures
  ON signatures.id = items.payload->>'orderSourceSignatureId'
WHERE items.payload->>'orderSourceSignatureId' IS NULL
   OR signatures.id IS NULL;
```

```sql
SELECT COUNT(*) AS sparse_signature_count
FROM order_source_signatures
WHERE COALESCE(payload->>'rawProductNameSnapshot', '') = ''
  AND COALESCE(payload->>'rawOptionInfoSnapshot', '') = '';
```

문제가 있으면 먼저 signature backfill 스크립트를 작성한다.

## 최종 성공 조건

2단계 완전 정규화 기준:

4. 주문 목록 상품명/옵션명 검색이 signature 기반으로 정상 동작한다.
5. 주문 목록 표시값은 기존과 동일하게 보인다.
6. 수동 주문 매핑 저장이 정상 동작한다.
7. 자동 주문 매핑 재계산이 정상 동작한다.
8. 함께배송 판별이 signature raw option 기준으로 유지된다.
9. 마진/일별 손익 조회가 정상 동작한다.
10. backend 테스트와 typecheck가 통과한다.

## 롤백 계획

코드 롤백:

- `OrderItem` 타입과 write/read path를 기존 방식으로 되돌리면 이후 새 동기화부터 중복 필드를 다시 저장할 수 있다.

데이터 롤백:

- `order_items`에서 제거한 raw/normalized/sourceSignature 필드는 DB 내부에서 자동 복구되지 않는다.
- 복구하려면 `order_source_signatures` join으로 backfill할 수 있다.

복구 SQL 방향:

```sql
UPDATE order_items items
SET payload =
  jsonb_set(
    jsonb_set(
      jsonb_set(
        jsonb_set(
          jsonb_set(items.payload, '{rawProductName}', to_jsonb(signatures.payload->>'rawProductNameSnapshot'), true),
          '{rawOptionInfo}', COALESCE(to_jsonb(signatures.payload->>'rawOptionInfoSnapshot'), 'null'::jsonb), true
        ),
        '{normalizedProductName}', to_jsonb(signatures.payload->>'normalizedProductName'), true
      ),
      '{normalizedOptionInfo}', to_jsonb(signatures.payload->>'normalizedOptionInfo'), true
    ),
    '{sourceSignature}', to_jsonb(signatures.payload->>'sourceSignature'), true
  ),
  payload_hash = NULL,
  updated_at = NOW()
FROM order_source_signatures signatures
WHERE signatures.id = items.payload->>'orderSourceSignatureId';
```

다만 롤백이 필요 없도록 read-path 전환과 테스트를 먼저 끝낸 뒤 마이그레이션을 실행하는 것이 핵심이다.
