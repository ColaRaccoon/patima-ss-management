# 6단계 - 성능 회귀 측정, 운영 문서, 최종 정리

## 새 세션 시작 프롬프트

```text
document/0604_수동매핑_쓰기성능_6단계_성능검증_문서화.md 파일을 읽고, 서브 에이전트 개발자/평가자 방식으로 끝까지 작업해줘.
```

## 필수 선행

먼저 [0604_수동매핑_쓰기성능_공통지침.md](./0604_수동매핑_쓰기성능_공통지침.md)를 읽는다.

이 단계도 반드시 공통 지침의 서브 에이전트 루프를 따른다. 개발자 에이전트가 구현하고, 평가자 에이전트가 결함을 하나라도 발견하면 재작업을 지시하며, 평가자가 합격할 때까지 반복한다.

1~5단계가 완료되지 않았다면 이 단계를 시작하지 않는다.

## 목표

1~5단계 결과가 실제로 수동 매핑 저장 지연을 줄였는지 확인하고, 운영자가 안전하게 유지보수할 수 있도록 문서를 정리한다.

## 작업 범위

필수:

1. `scripts/report-db-size.mjs`로 현재 DB 규모를 다시 확인한다.
2. 수동 매핑 저장 성능을 측정할 수 있는 안전한 절차를 문서화한다.
   - 실 DB 변경이 필요한 측정은 사용자 승인 없이 실행하지 않는다.
   - 가능하면 테스트 fixture 또는 임시 테스트 DB를 사용한다.
3. rawPayload prune 절차를 운영 문서에 정리한다.
   - 실행 전 backup/export
   - backend 중지 권장
   - dry-run
   - `--yes` 실행
   - 실행 후 report
4. 수동 매핑 저장 경로가 더 이상 전체 snapshot persistence를 타지 않는지 테스트 또는 코드 리뷰로 확인한다.
5. README 또는 scripts README에 다음을 남긴다.
   - 현재 PostgreSQL 저장 구조
   - 수동 매핑 hot path 개선 내용
   - rawPayload retention 운영 방법
   - 집/회사 DB 동기화 시 주의사항

## 성능 측정 기준

권장 기준:

- 기존 15~20초 수동 매핑 저장이 단건/소량 batch 기준 1~3초 이하로 줄어야 한다.
- 큰 batch나 여러 날짜에 걸친 매핑은 날짜 수와 대상 row 수에 비례해야 한다.
- `hasPendingWrite`가 장시간 true로 남지 않아야 한다.
- 읽기 API 응답 속도는 기존 수준을 유지해야 한다.

## 하지 말아야 할 것

- 실 DB에 임의 수동 매핑 POST를 승인 없이 실행하지 않는다.
- prune `--yes`를 승인 없이 실행하지 않는다.
- 성능 숫자를 측정하지 않고 추정만으로 완료 처리하지 않는다.

## 테스트 기준

필수:

- backend test/typecheck 통과
- 가능하면 전체 lint 통과
- DB size report 정상 실행
- 수동 매핑 hot path 관련 테스트 통과

명령 예시:

```powershell
npm run test --workspace @patima/backend
npm run typecheck --workspace @patima/backend
npm run lint
node scripts/report-db-size.mjs
```

## 평가자 체크리스트

- 문서가 실제 코드와 일치하는가
- 운영자가 rawPayload prune을 안전하게 실행할 수 있는가
- 실 DB 변경이 필요한 작업에 승인 조건이 명시되어 있는가
- 성능 목표와 측정 결과가 남아 있는가
- 이전 단계의 구현이 최종적으로 서로 충돌하지 않는가

## 완료 조건

- 평가자 에이전트 합격
- 테스트/타입체크 통과
- 성능 측정 또는 안전한 대체 검증 완료
- 운영 문서 업데이트 완료
