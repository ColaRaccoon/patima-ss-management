# 주문 동기화 안정화 구현·검증 결과

작성일: 2026-09-18

## 후속 수정: 가구매 저장 응답 시간 초과

2026-09-19 제보된 가구매 저장 오류의 문구는 공통 프록시에 추가했던 25초 제한에서 발생했다. 읽기 전용 조회로 해당 스토어의 2026-09-18 금액 389,000원이 이미 저장되어 있음을 확인했다. 시간 초과가 저장 취소를 뜻하지 않는 사례다. 공통 프록시의 제한은 명시한 비동기 주문 접수·상태 조회 경로에만 적용하고, 가구매 등 기존 동기 저장은 임의의 25초 제한을 적용하지 않도록 복원했다.

가구매의 PostgreSQL 저장은 전체 스냅샷을 처리하던 경로에서 해당 스토어·날짜의 금액과 감사 이력만 함께 저장하는 경로로 변경했다. 커밋 성공 후 메모리에 반영하며 파일 모드의 원자적 저장은 유지한다. 상품 매출 계산식은 변경하지 않는다. 실제 운영 데이터를 다시 저장하는 검증은 수행하지 않았다.

## 후속 요구 반영: 기본 조회를 어제 하루로 변경

사용자 후속 요청에 따라 아래 최초 구현의 기본 30일/CURRENT 동작을 변경했다. 화면의 기본 선택 날짜는 기존과 동일하게 한국시간 전날이다. 전체 스토어 버튼과 선택 날짜 버튼은 선택한 하루의 결제 주문만 요청한다. ‘어제 주문 동기화’ 및 날짜 없는 기본 API 요청은 서버 접수 시각을 기준으로 한국시간 전날 하루를 고정한다. 30일 변경 이력이나 기존 주문 ID 전체를 덧붙여 조회하지 않으며 전체 변경 수집 watermark를 갱신하지 않는다.

기접수 CURRENT/RECENT_30_DAYS 작업과 해당 작업의 재시도는 원래 범위를 보존한다. 이미 실행 중인 작업을 취소하거나 범위를 바꾸지는 않았다. 아래 성능·검증 기록은 앞선 안정화 구현 시점의 기록이다.

## 구현 내용

완료 후 상태 조회가 계속되던 문제도 후속 수정했다. 개발자·평가자 검토에서 접수 응답 유실 시 조회 재개, 다른 탭의 완료 작업 변경 반영, 여러 상세 조회 중 일부 실패 시 갱신 요청 복구를 보완했다. `node --import tsx scripts/test-order-sync-polling.ts`는 실제 provider 코드를 모의 hook·타이머·fetch 환경에서 실행하여 유휴 상태 60초 동안 추가 요청 없음, 완료 후 중지, 동일 URL 재접수, 오류 복구, 진행 중 요청과 재개 신호의 충돌, 응답 유실, 다른 탭 갱신, 정리를 검증한다. 테스트와 프런트엔드 타입 검사, 기존 응답 계약 검사가 통과했다. 실제 운영 브라우저·네이버 API 호출 검증은 이번 수정에 포함하지 않았다.

- 단일·전체·실패 재시도에 영속 배치, 동일 기준시각, 멱등키, 스토어별 결과를 적용했다. 접수는 원자적으로 저장하고 HTTP 202를 유지한다. 비활성은 제외, 인증 미설정·복호화 실패는 해당 스토어의 실패다. 운영 주문 동기화의 mock fallback을 제거했다.
- CURRENT는 화면 날짜 필터와 분리했다. 최초 최근 30일 결제/변경 수집과 저장된 기존 ID 상세 확인, 이후 변경 watermark의 5분 overlap 및 최근 결제 재조회를 결합한다. 수동 재수집은 성공 변경 watermark를 전진시키지 않는다.
- 네이버 요청은 실제 fetch/body abort, 제한된 재시도, 토큰 single-flight, 인증 갱신 1회, 요청 간격 제한을 사용한다. 페이지·커서 반복, 페이지 상한, 잘못된 schema, 상세 누락/중복/예상 밖 ID를 실패로 처리한다. 공식 schema와 한계는 [NAVER_ORDER_API_CONTRACT.md](./NAVER_ORDER_API_CONTRACT.md)에 기록했다.
- 청크 단위 멱등 저장과 checkpoint를 연결하고, 주문 변경 전후 영향 날짜를 집계한다. 주문 저장과 집계 실패를 구분하며 집계만 재실행하는 API/UI를 추가했다. lease owner/attempt fencing, 비중첩 heartbeat, 무진척 감시, 최종 결과·스토어 상태·watermark의 일관된 확정을 적용했다.
- 30일 초과 공백은 앱의 보수적 검증 정책으로 COVERAGE_GAP을 남긴다. 30일은 네이버의 보존기간 보장이 아니다. 최근 범위·기존 ID를 복구하더라도 미발견 과거 주문의 완전 수집을 주장하지 않는다. 명시적 공백 인정은 별도 변경 수집 기준선만 설정하며 원래 실패·성공 watermark·과거 공백 이력을 보존한다.
- 공통 provider/panel에 접수, 대기, 진행 단계, 재시도, 일부 실패, 제외, 공백·집계 경고를 표시한다. 서버 활성 배치 및 URL로 복원하고, 연결 장애 중 마지막 상태를 유지한다. 활성 작업이 없음을 확인하면 상세와 활성 목록의 반복 조회를 모두 멈춘다. 새 요청, 같은 브라우저의 다른 탭에서 보낸 접수 알림, 화면 복귀 및 재접속 시 조회를 재개한다. 다른 브라우저에서 접수한 작업은 화면 복귀나 새로고침 시 발견한다. 진행 건수마다 전체 페이지를 새로고침하지 않는다.
- 추가 JSONB 테이블/파일 컬렉션은 order_sync_batches, order_sync_batch_items, order_sync_states다. 레거시 기본값, queueOwned 정책, 백업 목록 및 배치에서 참조하는 operation의 prune 보호를 추가했다.

## 개발자–평가자 반복 검토

백엔드 개발자, 네이버 수집 개발자, 독립 평가자 등 서브에이전트 3개를 사용했다. 주 에이전트는 프런트엔드 개발과 통합 검증을 담당했다.

평가자가 raw 보관기간 회귀, 성공 후 이전 오류 잔존, 최종 실패 시 스토어 상태 불일치, DB 단절 상태 조회, 변경 overlap, coverage 재개·과거 인정 재전송, 종료시각 변동, UI 응답 검증·URL 복원·페이지 누락·공백 표시를 지적했다. 개발자가 수정하고 평가자가 회귀 테스트와 재검토를 반복했다. 마지막 교차검토에서는 기존 operation 재시도 경로의 멱등키 전달도 보완했다.

추가로 비활성 스토어 재시도 결과 연결, UTC→KST 결제일 변환, 미래 전용 범위의 조회 없는 성공 차단, 완료 배치의 UI 메모리 상한, 안전한 단계별 구조화 로그, 청크/worker 실행 양보를 검토했다. 최종 독립 검토에서 발견된 미해결 코드 결함은 없었다. 이는 아래 미검증 운영 환경까지 무결함을 보장한다는 의미는 아니다.

## 검증 근거

- 변경 전 `npm run test`: 통과.
- 변경 후 `npm run test`: 135개 PASS 항목. 기존 광고·매핑·주문·raw 보관 회귀 및 새 배치/파일 복원/lease/coverage/Naver fault 테스트 통과.
- `npm run lint`: shared/backend/frontend 타입 검사 통과.
- `node --import tsx scripts/test-order-sync-contract.ts`: 성공 envelope, 잘못된 목록·타임스탬프, false success, HTML, HTTP 오류 검증 통과.
- `$env:NEXT_DIST_DIR='.next-verify'; npm run build`: 전체 production build 통과. 기본 `.next` 경로의 파일 누락 오류가 반복되어 별도 출력 디렉터리에서 검증했다. `NEXT_DIST_DIR` 미설정 시 기존 `.next`를 유지한다. 빌드에서 확인된 Suspense 경계 누락도 수정했다.
- 격리된 HTTP fixture + 실제 브라우저 DOM: 전체 요청 CURRENT/멱등키, HTTP 202, 접수 중/버튼 비활성, 상세 조회 단계, 마지막 상태 보존, 일부 실패와 복구 버튼, URL 기준 새로고침 복원 확인. 화면 데이터는 합성 fixture이며 운영 주문이 아니다.
- 실제 임시 파일 저장으로 같은 키 동시 접수, DB 재오픈 후 배치 복원, 접수 실패 rollback을 검증했다. PostgreSQL fake harness 결과와 실제 PostgreSQL 검증은 구분한다.

## 합성 성능 검증

`node --import tsx scripts/order-sync-benchmark.ts 100 document/ORDER_SYNC_BENCHMARK_RESULT.json`으로 6개 스토어 × 각 100/300개 주문상품을 100회씩 동기화한다. 실제 파일 저장·worker 실행·매핑·손익 집계를 사용하되 네이버 stream은 합성 fixture이며 외부 fetch는 차단한다. 같은 ID 재처리의 중복 방지를 확인하는 테스트로, 주문 이력이 계속 증가하는 장기 부하와는 다르다.

최초 측정에서는 총 1,200개 작업의 실패·영구 대기·주문 중복은 0이었지만 3배 데이터의 이벤트 루프 최대 지연이 5,758.78ms였다. 동기 파일 저장과 연속 microtask 실행의 응답 지연을 줄이기 위해 청크의 커밋·checkpoint 기록 후 및 worker 작업 사이에 `setImmediate` 양보를 추가했다. 커밋 중에는 양보하지 않으며 순차 실행·lease·fencing을 유지한다. 수정 전 결과는 [ORDER_SYNC_BENCHMARK_BEFORE_YIELD.json](./ORDER_SYNC_BENCHMARK_BEFORE_YIELD.json)에 보존했다.

## 운영 적용 전 남은 검증

- 실제 PostgreSQL 테스트 DB에서 트랜잭션·advisory lock·접수 중단·재시작·백업 export/import 왕복 검증은 수행하지 못했다. 로컬 Docker 명령은 데몬 미실행으로 실패했다. 운영 DATABASE_URL에는 연결하지 않았다.
- 실제 네이버 smoke test와 사용자가 보고한 약 6회 중 1회 실패/프로세스 ‘터짐’은 재현하지 않았다. 이번에 확인한 코드 결함을 그 현상의 확정 원인으로 단정하지 않는다.
- 운영 DB 크기는 조사하지 않았다. 합성 1배/3배 결과를 운영 규모의 1배/3배 검증으로 해석하면 안 된다. HTTP API p95와 UI 5초 반영의 자동화된 장시간 측정도 별도 필요하다.
- 단일 백엔드 프로세스·순차 worker가 지원 범위다. PostgreSQL 청크 경로에도 메모리 배열 스캔과 스토어 상품/시그니처 복제 비용이 남고, 파일 모드에는 전체 JSON 저장 비용이 남는다.
- 운영 배포·데이터 초기화·실제 주문 동기화는 수행하지 않았다. 배포 전 기존 백업·복원 절차를 확인하고 구버전 worker를 drain/중지한 뒤 additive schema를 적용해야 한다.
