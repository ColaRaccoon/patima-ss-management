핵심 요약

가장 큰 장기 리스크는 PostgreSQL을 사용하더라도 실제로는 모든 테이블을 JSONB 스냅샷 저장소처럼 다루는 구조입니다. 요청마다 메모리 전체 스냅샷을 읽고, 쓰기마다 전체 DB를 복제한 뒤, PostgreSQL에서는 모든 테이블을 TRUNCATE 후 재삽입합니다. 현재 백업만 보아도 2026-05-22 기준 백업 파일이 약 349MB까지 커져 있어, 운영 기간이 늘어나면 쓰기 지연, DB 락, 메모리 증가, 백업/복구 시간 증가가 빠르게 현실화될 가능성이 큽니다.

주문 데이터는 “원본 전체 영구 보관”보다 계산에 필요한 핵심 필드와 일별 결과는 장기 보관하고, 네이버 원본 rawPayload는 최근 30~90일만 운영 DB에 두는 방식이 효율적입니다. 한 달이 지난 원본 주문을 무조건 삭제하기보다는, 월 마감 후 압축 archive로 분리하고 운영 DB에는 결과값과 최소 추적 필드만 남기는 구조를 권장합니다.

권장 데이터 보관 구조

주문 전체 원본을 계속 DB에 저장하는 방식은 장기적으로 비효율적입니다. 다만 원본 주문을 한 달 뒤 바로 전부 삭제하고 결과값만 남기면, 취소/반품 지연 반영, 과거 마진 재검산, 감사 추적, 계산식 변경 대응이 어려워질 수 있습니다. 따라서 운영 DB, 집계 결과, archive를 나누는 구조가 가장 안전합니다.

주문/주문상품 핵심 필드 장기 보관 장기 보관 주문번호, 상품주문번호, 결제일, 판매상태, 상품명, 옵션, 수량, 매출, 수수료, 배송비, 매핑 판매단위 등 계산과 추적에 필요한 값만 남깁니다.
일별 판매단위 마진 결과 장기 보관 장기 보관 daily_sales_unit_profit, daily_store_summary 같은 결과 테이블을 두고 화면/엑셀은 이 결과를 우선 사용합니다.
광고비 일별 결과 장기 보관 장기 보관 광고 원본 파일 전체보다 일자, 캠페인, 비용, 매핑 결과 중심으로 유지합니다.
원가 스냅샷/매핑 이력 장기 보관 장기 보관 과거 결과를 설명하는 기준 데이터이므로 삭제하지 않습니다.
audit/operation 로그 최근 N일 또는 N건 archive 운영 화면에는 최근 로그만 두고, 과거 로그는 압축 보관합니다.

근거
scripts/db-import.mjs는 모든 table을 TRUNCATE하고 각 row를 반복 insert합니다.
장기 증상
데이터가 커질수록 복구 중 다운타임이 길어집니다. 중간 실패 시 rollback되지만, 운영 백엔드가 살아 있으면 snapshot-replace와 충돌할 수 있다는 주석도 있습니다.
보완
복구 절차를 운영 중지, 백업 검증, restore, smoke test, 재기동 순서로 문서화합니다. 대용량은 COPY 또는 pg_restore 계열로 전환합니다.
중 Docker 빌드와 운영 설정이 재현성/준비성 측면에서 약함
근거
Dockerfile은 node:24-alpine과 npm install을 사용하고, docker-compose.yml은 DB readiness healthcheck 없이 depends_on만 둡니다.
장기 증상
패키지/Node 버전 변화로 빌드 결과가 달라질 수 있고, 백엔드가 DB 준비 전 기동 실패할 수 있습니다.
보완
Node LTS 버전 고정, npm ci, DB healthcheck, backend restart policy, readiness/liveness endpoint를 구성합니다.
중 마이그레이션 실행 체계가 약하고 스키마 진화가 코드 normalize에 의존함
근거
migrations/에는 수동 SQL이 있고, database.service.ts는 부팅 시 JSONB table만 보장합니다. 필드 추가는 normalizeSnapshot()에서 보정하는 방식입니다.
장기 증상
PC/서버마다 migration 적용 상태가 달라질 수 있습니다. 데이터 구조가 커질수록 normalize 비용도 커집니다.
보완
마이그레이션 도구를 도입하고 schema version을 DB에 기록합니다. 배포 시 migration 실행과 rollback 절차를 분리합니다.

유지보수성과 데이터 품질

중 소스 일부 한글 문자열이 깨져 있어 운영 오류 대응이 어려움
근거
ads.service.ts, cost.service.ts, helpers.ts 등 여러 파일에 mojibake 형태의 메시지와 헤더 문자열이 남아 있습니다.
장기 증상
엑셀 헤더 매칭, 오류 메시지, 주석 해석이 어려워져 장애 대응 시간이 늘어납니다.
보완
UTF-8 기준으로 문자열을 복구하고, 엑셀 헤더는 상수/테스트 fixture로 관리합니다. 사용자 표시 메시지와 내부 reason code를 분리합니다.
중 원가 스냅샷 import가 메타 수정과 비용 적용을 한 작업에 섞음
근거
cost.service.ts:459-581은 엑셀 import 중 판매단위 메타를 수정/생성하고 동시에 비용 snapshot/entry를 만듭니다.
장기 증상
잘못된 엑셀 파일 하나가 판매단위 메타와 원가를 함께 바꿉니다. 되돌리기/감사 추적이 복잡합니다.
보완
메타 변경 preview, 비용 snapshot preview, confirm 단계를 분리합니다. import 결과 diff를 보여주고 승인 후 반영하도록 바꿉니다.
하 운영 관측 지표가 부족함
근거
health는 단순 ok: true만 반환합니다. DB 지연, queue 길이, 마지막 sync, persistence 실패 수 같은 지표가 없습니다.
장기 증상
느려진 원인을 백업 크기, DB 쓰기 지연, API 장애, 계산 병목 중 어디에서 찾아야 할지 늦게 알게 됩니다.
보완
health에 DB ping과 storage mode를 포함하고, operation duration, sync failure, persistence failure, backup age를 로그/대시보드화합니다.

권장 보완 순서

단계 목표 작업 완료 기준
1단계 운영 사고 방지 관리자 인증, CORS 제한, 운영 mock fallback 차단, MASTER_KEY 필수화, 업로드 크기 제한 외부에서 인증 없이 쓰기 API 호출 불가, 운영에서 mock 데이터 미표시
2단계 데이터 손실 방지 PostgreSQL 쓰기 commit 후 응답, persistence error 노출, 중첩 write 제거, 파일 모드 경로 정리 쓰기 성공 응답은 DB 저장 완료를 의미하고 audit log가 유실되지 않음
3단계 성능 병목 제거 주문/광고/비용/작업 목록을 DB 쿼리 기반 페이지네이션으로 전환, 주요 인덱스 추가 10만~100만 row 기준 목록 조회가 일정한 시간 내 응답
4단계 마진 계산 안정화 daily summary/materialized view 도입, 결과 테이블 저장, 변경 날짜만 증분 재계산 마진 화면과 export가 기간 증가에 선형 폭증하지 않고, 마감된 날짜는 결과값 중심으로 조회
5단계 장기 보관 체계 rawPayload 최근 30~90일 보관, 월 마감 후 archive/delete, audit/operation archive, 백업 암호화와 restore 리허설 운영 DB 크기 증가가 통제되고, 과거 결과 추적과 복구 시간이 예측 가능함
6단계 확장 가능한 작업 실행 DB/Redis 기반 job queue, heartbeat, progress, retry/backoff, 네이버 API rate limit 재시작/장애 후에도 작업 상태를 정확히 복구
단기적으로 전부 갈아엎기 어렵다면, 먼저 보안 잠금 + 저장 실패를 숨기지 않기 + rawPayload 단기 보관 전환 + 일별 결과 저장 + 목록 조회 DB 페이지네이션을 잡는 것이 효과가 큽니다.
