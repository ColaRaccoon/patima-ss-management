# 0616 수정계획 - 주문 rawPayload 운영 DB 제거

## 목적

이번 작업의 목적은 `orders`, `order_items`에 저장되는 네이버 주문 원본 JSON인 `rawPayload`를 운영 DB에서 제거하고, 새 주문 동기화 중에도 기본적으로 rawPayload 객체를 만들지 않도록 바꾸는 것이다.

여기서 "제거"는 주문 row나 주문상품 row를 삭제하는 것이 아니다. 기존 타입과 조회 로직의 호환성을 유지하기 위해 DB payload의 `rawPayload` 키는 남기되 값만 `null`로 만든다. 새 주문 동기화는 기본적으로 네이버 원본 상세 응답을 `rawPayload` 객체로 만들지 않고, `rawPayload: null`만 흘려보내도록 정책을 바꾼다.

이번 범위는 `rawPayload`의 DB 저장 제거와 생성 기본 비활성화까지다. `order_items`의 상품명, 옵션명, 정규화 텍스트, 시그니처 같은 반복 필드를 줄이는 정규화 작업은 다음 단계로 분리한다.

## 현재 결론

2026-06-16 기준 실제 로컬 PostgreSQL DB 측정 결과, `rawPayload` 제거 효과가 가장 크다.

현재 측정값:

| 항목 | 값 |
| --- | ---: |
| 전체 payload 크기 | 218,595,840 bytes |
| 전체 PostgreSQL relation 크기 | 296,222,720 bytes |
| 전체 DB 크기 | 305,510,067 bytes |
| `orders + order_items` payload | 210,793,016 bytes |
| `orders + order_items`가 전체 payload에서 차지하는 비중 | 96.43% |
| `rawPayload`를 null 처리했을 때 예상 절감량 | 128,111,883 bytes |
| 전체 payload 기준 절감률 | 58.61% |
| 전체 relation 기준 절감률 | 43.25% |
| 전체 DB 기준 절감률 | 41.93% |

테이블별 측정값:

| 테이블 | rows | 현재 payload | rawPayload null 후 예상 | 예상 절감 | 테이블 내 절감률 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `orders` | 31,658 | 85,344,972 bytes | 13,124,463 bytes | 72,220,509 bytes | 84.62% |
| `order_items` | 40,992 | 125,448,044 bytes | 69,556,670 bytes | 55,891,374 bytes | 44.55% |

백업/export처럼 JSON 텍스트로 펼쳐지는 기준에서는 절감 효과가 더 크다.

| 항목 | 값 |
| --- | ---: |
| 전체 payload JSON 텍스트 크기 | 378,438,712 bytes |

| JSON 텍스트 기준 절감률 | 76.85% |

주의: PostgreSQL에서 JSON 값을 `null`로 바꿔도 실제 디스크 파일 크기가 즉시 줄어들지는 않을 수 있다. 논리적 payload 크기는 줄지만, 물리적 디스크 회수는 `VACUUM FULL`, dump/restore, export/import 같은 테이블 재작성 작업이 필요할 수 있다.

## 현재 코드 구조

### 1. 네이버 주문 응답 파싱

파일: `apps/backend/src/naver-commerce.service.ts`

핵심 위치:

- `SyncedOrderItemInput` 인터페이스
- `fetchOrderItems(storeId, dateFrom, dateTo)`
- `normalizeOrderDetail(detailEnvelope, changedOrder)`

현재 흐름:

1. 결제일 기준으로 상품주문번호 목록을 조회한다.
2. 상품주문번호 배치로 상세 주문을 조회한다.
3. `normalizeOrderDetail()`에서 네이버 응답을 `SyncedOrderItemInput`으로 변환한다.
4. 업무에 필요한 핵심 필드는 개별 필드로 파싱한다.
5. 네이버 상세 응답 원본 전체는 아래 형태로 `rawPayload`에 담는다.

```ts
rawPayload: {
  changedOrder: changedOrder ?? null,
  detail: detailEnvelope,
}
```

현재 파싱해서 업무 필드로 사용하는 데이터:

- `externalOrderId`
- `externalProductOrderId`
- `externalProductId`
- `rawProductName`
- `rawOptionInfo`
- `optionCode`
- `optionManageCode`
- `quantity`
- `productPaymentAmount`
- `totalProductAmount`
- `deliveryFeeAmount`
- `paymentCommission`
- `knowledgeShoppingSellingInterlockCommission`
- `saleCommission`
- `channelCommission`
- `orderDate`
- `paymentDate`
- `orderDateTime`
- `paymentDateTime`
- `productOrderStatus`
- `claimStatus`
- `rawStatus`
- `saleStatus`
- `packageNumber`

`rawPayload.detail` 안에만 남고 업무 필드로 직접 쓰지 않는 데이터:

- 구매자/수취인 개인정보
- 주소/연락처
- 결제수단 상세
- 할인/쿠폰/포인트 상세
- 배송 추적 상세
- 클레임 상세 이력
- 네이버 응답의 기타 중첩 필드

이번 작업에서는 `normalizeOrderDetail()`이 transient 객체에 `rawPayload`를 항상 만드는 흐름도 바꾼다. 기본 정책이 `ORDER_RAW_PAYLOAD_RETENTION_DAYS=0`이면 DB에 저장하지 않을 원본 JSON을 동기화 중 메모리에 붙잡고 있을 이유가 적다.

변경 방향:

- `SyncedOrderItemInput.rawPayload` 타입을 `Record<string, unknown> | null`로 바꾼다.
- `fetchOrderItems()` 또는 `normalizeOrderDetail()`에 `includeRawPayload` 옵션을 추가한다.
- `includeRawPayload`가 `false`이면 `rawPayload: null`을 반환한다.
- `includeRawPayload`가 `true`이면 기존처럼 `{ changedOrder, detail }`을 만든다.
- `OrderSyncService.performSync()`가 `rawPayloadRetentionDays > 0`일 때만 `includeRawPayload: true`를 넘긴다.

이렇게 하면 운영 기본값에서는 원본 JSON을 DB에도 저장하지 않고, 동기화 중 `entries` 배열에도 큰 rawPayload 객체를 붙이지 않는다. 단, 긴급 디버깅이나 원본 재처리가 필요하면 `ORDER_RAW_PAYLOAD_RETENTION_DAYS=30` 또는 `90`처럼 양수로 설정해 기존 원본 저장 경로를 다시 켤 수 있다.

### 2. 주문 동기화와 DB 저장

파일: `apps/backend/src/order-sync.service.ts`

핵심 위치:

- `performSync()`
- `retainedRawPayload`
- `existingOrder.rawPayload = retainedRawPayload`
- 신규 `OrderRecord.rawPayload`
- 신규/갱신 `OrderItem.rawPayload`

현재 흐름:

```ts
const rawPayloadReferenceDate = getSyncedOrderItemRetentionDate(entry);
const retainedRawPayload = shouldRetainOrderRawPayload(
  rawPayloadReferenceDate,
  rawPayloadRetentionCutoffDate,
  rawPayloadRetentionDays,
)
  ? entry.rawPayload
  : null;
```

`retainedRawPayload`가 다음 두 곳에 저장된다.

- `orders.rawPayload`
- `order_items.rawPayload`

따라서 `rawPayloadRetentionDays`가 `0`이면 `shouldRetainOrderRawPayload()`가 항상 `false`가 되어 새 동기화 row는 `rawPayload: null`로 저장된다.

### 3. rawPayload 보관 정책

파일: `apps/backend/src/raw-payload-retention.ts`

현재 주요 함수:

- `DEFAULT_ORDER_RAW_PAYLOAD_RETENTION_DAYS`
- `getOrderRawPayloadRetentionDays()`
- `getKstRetentionCutoffDate()`
- `getSyncedOrderItemRetentionDate()`
- `shouldRetainOrderRawPayload()`
- `pruneExpiredOrderRawPayloads()`

현재 기본값:

```ts
export const DEFAULT_ORDER_RAW_PAYLOAD_RETENTION_DAYS = 90;
```

현재 정책:

- 환경변수 `ORDER_RAW_PAYLOAD_RETENTION_DAYS`가 없으면 90일 보관
- 값이 `0`이면 새 동기화 주문도 원본 payload를 저장하지 않음
- 잘못된 값, 음수, 소수는 기본값으로 fallback

이번 작업에서 바꿀 정책:

- 기본값을 `0`으로 변경한다.
- 환경변수를 명시하지 않아도 새 동기화는 `rawPayload`를 저장하지 않는다.
- 디버깅 목적으로 원본 보관이 필요할 때만 `ORDER_RAW_PAYLOAD_RETENTION_DAYS=30` 또는 `90`처럼 명시한다.

### 4. 기존 rawPayload 정리 스크립트

파일: `scripts/prune-order-raw-payloads.mjs`

이미 재활용 가능한 스크립트다. 새로 만들 필요 없다.

기능:

- PostgreSQL `orders.payload.rawPayload`
- PostgreSQL `order_items.payload.rawPayload`
- row는 유지하고 `rawPayload` 값만 JSON `null`로 변경
- 기본 dry-run
- `--yes`를 붙여야 실제 변경
- KST 기준 cutoff 적용
- `--days 0`이면 모든 non-null `rawPayload`가 정리 대상

실행 예:

```powershell
node scripts/prune-order-raw-payloads.mjs --days 0
node scripts/prune-order-raw-payloads.mjs --days 0 --yes
```

주의:

- 이 스크립트는 현재 PostgreSQL 전용이다.
- `DATABASE_URL`이 없으면 실패한다.
- 현재 프로젝트 `.env`에는 `DATABASE_URL=postgresql://patima_app:...@localhost:5432/patima_naver_ss`가 있으므로 로컬 기준으로는 PostgreSQL 대상이 맞다.
- 실행 시 `payload_hash = NULL`로 둔다. 이후 backend의 snapshot persistence가 해당 row를 다시 쓸 때 실제 payload 기준 hash가 재계산된다.

### 5. DB 크기 리포트 스크립트

파일: `scripts/report-db-size.mjs`

이미 재활용 가능한 스크립트다.

기능:

- `orders`, `order_items`의 `rawPayload` non-null/null count 출력
- 큰 payload row 상위 목록 출력

작업 전후 모두 실행해야 한다.

```powershell

```

## 수정해야 할 코드와 문서

### 필수 코드 수정

#### 1. `apps/backend/src/naver-commerce.service.ts`

변경 대상:

- `SyncedOrderItemInput`
- `fetchOrderItems()`
- `normalizeOrderDetail()`

변경 전 타입:

```ts
rawPayload: Record<string, unknown>;
```

변경 후 타입:

```ts
rawPayload: Record<string, unknown> | null;
```

권장 구현 방향:

```ts
async fetchOrderItems(
  storeId: string,
  dateFrom: string,
  dateTo: string,
  options?: { includeRawPayload?: boolean },
): Promise<SyncedOrderItemInput[]> {
  // ...
  return details
    .map((detail) =>
      this.normalizeOrderDetail(detail, undefined, {
        includeRawPayload: options?.includeRawPayload === true,
      }),
    )
    .filter((item): item is SyncedOrderItemInput => !!item);
}
```

`normalizeOrderDetail()` 권장 변경:

```ts
private normalizeOrderDetail(
  detailEnvelope: JsonRecord,
  changedOrder: JsonRecord | undefined,
  options?: { includeRawPayload?: boolean },
): SyncedOrderItemInput | null {
  // ...
  rawPayload: options?.includeRawPayload
    ? {
        changedOrder: changedOrder ?? null,
        detail: detailEnvelope,
      }
    : null,
}
```

의도:

- 운영 기본값에서는 네이버 상세 응답 전체를 `rawPayload` 객체로 만들지 않는다.
- DB 저장 전 retention 로직에서 버릴 데이터를 굳이 `entries` 배열에 붙이지 않는다.
- 원본 저장이 필요할 때는 `includeRawPayload: true`로 기존 경로를 살린다.

주의:

- 업무 필드 파싱은 그대로 유지한다.
- `detailEnvelope` 자체를 파싱에 사용한 뒤 버리는 것은 괜찮다.
- `rawPayload` 객체만 만들지 않는 것이지, 네이버 API 응답을 덜 받는 것은 아니다.
- 네이버 API가 필드 선택을 지원하는지 확인되지 않았으므로 이번 작업은 API 응답 축소가 아니라 앱 내부 보관 축소다.

#### 2. `apps/backend/src/order-sync.service.ts`

변경 대상:

- `performSync()`
- `this.naverCommerceService.fetchOrderItems(...)` 호출부

```ts
  ? await this.naverCommerceService.fetchOrderItems(storeId, dateFrom, dateTo, {
```

```ts
private generateMockItems(
  dateFrom: string,
  dateTo: string,
  options?: { includeRawPayload?: boolean },

  // ...
```

`retainedRawPayload` 계산은 null-safe하게 둔다.


- retention 양수일 때만 기존처럼 rawPayload를 만들고, cutoff 기준으로 DB 저장 여부를 결정한다.
- 기존 테스트와 mock fallback도 같은 정책을 따른다.

## 수정하지 말아야 할 것

이번 단계에서 아래 작업은 하지 않는다.

1. `orders` row 삭제
2. `order_items` row 삭제
3. `rawPayload` 키 자체 제거
4. `OrderRecord.rawPayload` 타입 제거
5. `OrderItem.rawPayload` 타입 제거
6. `SyncedOrderItemInput.rawPayload` 키 자체 제거
7. `order_items.rawProductName`, `rawOptionInfo`, `sourceSignature` 등 반복 필드 정규화
8. `orders`, `order_items`를 정규 컬럼 테이블로 재설계
9. 광고 데이터, 감사 로그, 작업 로그 정리

이유:

- 현재 주문 목록, 매핑, 마진 계산은 `rawPayload` 없이 동작하지만 타입은 `rawPayload: Record<string, unknown> | null`을 기대한다.
- 기존 테스트도 `rawPayload: null`을 정상 상태로 검증한다.
- 원본 JSON 제거와 order_items 정규화를 동시에 하면 영향 범위가 커진다.
- `SyncedOrderItemInput.rawPayload`는 optional이 아니라 `Record<string, unknown> | null`로 둔다. 키가 항상 있으면 이후 저장 로직과 테스트 fixture가 단순하다.

## 물리적 디스크 공간 회수

`rawPayload`를 `null` 처리하면 논리적 payload 크기는 줄어든다. 하지만 PostgreSQL은 업데이트 후 테이블 파일을 즉시 줄이지 않을 수 있다.

운영 중 즉시 디스크 회수가 꼭 필요하지 않다면 여기서 멈춰도 된다.

디스크까지 회수해야 한다면 별도 유지보수 시간에 아래 중 하나를 선택한다.

### 선택지 A - VACUUM FULL

예:

```sql
VACUUM FULL ANALYZE orders;
VACUUM FULL ANALYZE order_items;
REINDEX TABLE orders;
REINDEX TABLE order_items;
```

주의:

- `VACUUM FULL`은 테이블을 재작성하고 exclusive lock을 건다.
- backend를 중지하고 실행해야 한다.
- DB 크기와 환경에 따라 시간이 걸릴 수 있다.
- 이 작업은 사용자가 명시적으로 승인한 경우에만 실행한다.

### 선택지 B - export/import 또는 dump/restore

이미 프로젝트에는 `db-export.mjs`, `db-import.mjs`가 있다.

논리적으로 깨끗한 snapshot을 새 DB에 넣으면 공간 회수가 더 명확할 수 있다.

주의:

- `db-import.mjs --yes`는 대상 payload table을 `TRUNCATE` 후 재삽입한다.
- 대상 DB의 로컬 변경이 사라질 수 있다.
- 반드시 백업과 사용자 승인 후 진행한다.

## 롤백 계획

### 코드 롤백

`DEFAULT_ORDER_RAW_PAYLOAD_RETENTION_DAYS`를 다시 `90`으로 바꾸거나, 환경변수로 양수를 지정하면 이후 새 동기화부터 `rawPayload`를 다시 저장할 수 있다.

```env
ORDER_RAW_PAYLOAD_RETENTION_DAYS=90
```

### 데이터 롤백

기존 `rawPayload`를 `null`로 만든 뒤에는 DB 내부에서 원본을 복구할 수 없다.

복구 방법:

1. prune 전 `db-export` 백업을 `db-import.mjs --yes`로 복원
2. 또는 네이버 API에서 동일 기간 주문 상세를 재동기화하면서 `ORDER_RAW_PAYLOAD_RETENTION_DAYS`를 양수로 설정

주의:

- 네이버 API가 과거 주문 상세를 언제까지 동일하게 제공하는지 보장할 수 없다.
- 정확한 원본 JSON이 필요하면 prune 전 백업이 유일한 안전한 롤백 수단이다.

## 개인정보와 백업 주의사항

`rawPayload`에는 네이버 상세 주문 응답 전체가 들어간다. 구매자/수취인/배송/결제 관련 개인정보성 데이터가 포함될 수 있다.

작업 후에도 기존 백업 파일에는 rawPayload가 남아 있을 수 있다.

현재 큰 백업 파일 예:

- `backups/patima-2026-06-02T07-57-55-180Z.json`: 448,380,278 bytes
- `backups/patima-2026-06-01T07-18-29-963Z.json`: 440,098,503 bytes

이번 작업에서 운영 DB의 rawPayload를 제거해도 과거 백업의 rawPayload는 자동으로 제거되지 않는다.

백업 처리 원칙:

- 작업 전 백업은 롤백을 위해 일단 보관한다.
- 작업 검증 후 사용자가 승인하면 rawPayload 포함 과거 백업을 별도 암호화 보관하거나 삭제한다.
- 백업 삭제는 파괴적 작업이므로 사용자 명시 승인 없이 실행하지 않는다.

## 다음 단계로 넘길 작업

이번 작업이 끝난 뒤 고려할 수 있는 다음 단계는 `order_items` 정규화다.

다음 단계 후보:

- `normalizedProductName`, `normalizedOptionInfo` 제거 또는 재계산 방식 전환

하지만 이 작업은 주문 목록, 매핑, 자동매핑, 검색, 마진 계산 쿼리에 영향이 있으므로 rawPayload 제거와 동시에 진행하지 않는다.
