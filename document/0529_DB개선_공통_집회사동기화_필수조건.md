# 0529 DB 개선 공통 - 집/회사 DB 동기화 필수 조건

## 이 문서의 목적

이 문서는 DB 개선 단계 전체에서 절대 잃으면 안 되는 운영 요구사항을 명시한다.

요구사항:

> 어떤 방식이든 집 PC와 회사 PC의 DB 데이터를 완전히 동기화할 수 있는 수단은 계속 남아 있어야 한다.

현재는 `scripts/db-export.mjs`와 `scripts/db-import.mjs`로 PostgreSQL JSONB 저장 테이블을 JSON snapshot 파일로 내보내고, 다른 PC에서 전체 덮어쓰기 import를 수행할 수 있다. 이후 DB 구조가 바뀌더라도 이 기능은 반드시 유지하거나 더 안전한 방식으로 대체해야 한다.

## 현재 가능한 방식

현재 가능한 방식은 **단방향 전체 snapshot 동기화**다.

원본 PC:

```powershell
node scripts/db-export.mjs
```

대상 PC:

```powershell
node scripts/db-import.mjs backups/patima-xxxx.json --yes
```

조건:

- 대상 PC의 백엔드는 반드시 중지한다.
- 집/회사 `.env`의 `MASTER_KEY`는 같아야 한다.
- 양쪽 PC에서 동시에 서로 다른 데이터를 수정한 뒤 merge하는 방식은 지원하지 않는다.
- 한 번에 한 PC만 원본으로 정하고 다른 PC는 덮어쓴다.

## DB 개선 중 반드시 지킬 원칙

1. 모든 DB 개선 단계는 "전체 DB export/import 가능" 상태를 유지해야 한다.
2. schema가 바뀌면 `scripts/db-export.mjs`, `scripts/db-import.mjs`, `scripts/README.md`를 함께 업데이트해야 한다.
3. import는 대상 DB를 완전한 snapshot 상태로 만들 수 있어야 한다.
4. import 후 backend가 정상 기동하고 기존 데이터가 모두 조회되어야 한다.
5. export/import는 merge가 아니라 전체 교체 방식임을 문서에 계속 명시한다.
6. 중앙 클라우드 DB를 도입하기 전까지는 이 snapshot 이동 방식이 집/회사 동기화의 공식 수단이다.
7. 중앙 DB를 도입한 뒤에도 backup/restore 목적의 full export/import 수단은 유지한다.

## 단계별 영향

### 1단계 저장 안정화

기존 JSONB table 구조를 유지하므로 현재 export/import를 계속 사용할 수 있다.

단, `writeCommitted()`나 atomic write를 도입하더라도 import 시 백엔드 중지 조건은 유지한다.

### 2단계 row-level persistence

`payload_hash` 같은 보조 컬럼을 추가하면 현재 import 스크립트가 그대로는 부족할 수 있다.

필수 조치:

- export snapshot에 schema version을 기록한다.
- import 시 `payload_hash`를 함께 복원하거나 import 후 backfill한다.
- `payload_hash`는 nullable로 시작하거나, import 스크립트가 항상 값을 채우게 만든다.
- `TRUNCATE + 전체 재삽입`은 runtime persistence에서는 제거하더라도, 명시적 full restore 도구에서는 사용할 수 있다.

중요:

- "일반 API 쓰기"에서 `TRUNCATE`를 제거하는 것과 "사용자가 명시적으로 실행하는 전체 restore"에서 `TRUNCATE`를 쓰는 것은 다르다.
- import 스크립트는 백업 복원/PC 동기화 도구이므로 전체 교체 방식이어도 된다.

### 3단계 DB 조회 페이지네이션

조회 방식만 바꾸는 단계라 export/import 영향은 작다.

필수 조치:

- DB query에 필요한 index가 import 후에도 존재해야 한다.
- import 후 schema/index ensure가 실행되거나 import 스크립트가 index를 보장해야 한다.

### 4단계 일별 결과 테이블

`daily_sales_unit_profits`, `daily_store_summaries`가 추가되면 export/import 대상에 반드시 포함한다.

원칙:

- 완전 동기화를 위해 결과 테이블도 export/import한다.
- "필요하면 재계산 가능"하더라도 snapshot 동기화에서는 포함하는 것이 기본이다.
- import 후 summary 재계산 옵션은 보조 기능으로만 둔다.

### 5단계 보존/백업/아카이브

이 단계에서 export/import 스크립트를 공식 운영 도구로 정비한다.

필수 조치:

- `scripts/db-export.mjs`를 schema-aware full export로 개선한다.
- `scripts/db-import.mjs`를 schema-aware full restore로 개선한다.
- `scripts/report-db-size.mjs`에 snapshot export 가능 여부와 table 누락 여부를 표시한다.
- restore 리허설 문서에 집/회사 PC 이동 절차를 포함한다.

### 6단계 DB 작업 큐와 중앙 DB 준비

중앙 DB를 쓰게 되면 집/회사 동기화 방식은 "파일 이동"에서 "같은 중앙 DB 사용"으로 바뀔 수 있다.

그래도 다음은 유지한다.

- 중앙 DB 도입 전까지는 snapshot export/import를 공식 동기화 수단으로 유지한다.
- 중앙 DB 도입 후에도 full backup/restore/export/import는 유지한다.
- 중앙 DB를 도입하려면 row-level persistence와 DB 기반 operation queue가 먼저 완료되어야 한다.

## 금지 사항

- DB 구조를 바꾸면서 export/import를 깨진 상태로 방치하지 않는다.
- "나중에 만들면 된다"는 이유로 집/회사 동기화 수단을 없애지 않는다.
- snapshot import가 일부 table만 복원하는 상태를 "완전 동기화"라고 부르지 않는다.
- 양방향 merge를 지원하지 않으면서 자동 동기화라고 표현하지 않는다.

## 완료 기준

각 DB 개선 단계 완료 시 다음을 확인한다.

```powershell
node scripts/db-export.mjs
node scripts/db-import.mjs <방금 만든 snapshot.json> --yes
npm.cmd run typecheck --workspace @patima/backend
npm.cmd run test --workspace @patima/backend
```

실제 운영 DB에 import할 때는 사용자 확인 후 진행한다. 테스트에서는 임시 DB나 백업 DB를 사용한다.

## 다음 세션 공통 지시문

DB 개선 작업을 하는 모든 다음 세션은 아래 조건을 따라야 한다.

```text
DB 구조를 수정하더라도 집/회사 PC 간 전체 DB 동기화 수단은 반드시 유지해야 한다.
현재 공식 수단은 scripts/db-export.mjs / scripts/db-import.mjs 기반 전체 snapshot 이동이다.
schema나 table이 바뀌면 export/import 스크립트와 scripts/README.md를 함께 업데이트하라.
이 기능은 양방향 merge가 아니라 한쪽 원본을 다른 쪽에 덮어쓰는 단방향 full sync다.
중앙 DB 도입 전까지 이 수단을 깨면 안 된다.
```
