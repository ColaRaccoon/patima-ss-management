# 0421 수정계획.md — 대표 기준 손익(부가세 차감 매출 + 묶음 기준 배송원가)

> 작성일: 2026-04-20  
> 최종 개정: 2026-04-20 (설계 결정 반영)  
> 적용 기준: 기존코드관찰.md (2026-04-20 업데이트)  
> 목적: 세무용 정밀 계산이 아닌, **대표 내부 관리용** 손익 지표 도입.  
>   (1) 상품매출에 10% VAT를 차감한 "대표 기준 매출"을 손익 계산에 사용하되, 원본 상품매출은 화면 유지.  
>   (2) 배송비는 실제 묶음(`packageNumber` > `orderId`) 개수 × 배송단가로 추정하여 "스토어 부담 배송비"를 **스토어 레벨**에서 산출하고 대시보드 순이익에서 차감.

## 0. 요구사항 요약 (확정판)

### 매출(VAT)
- `productRevenueOriginal` — 기존 `totalProductRevenue` 그대로 (화면 표시용).
- `vatAmount = Math.round(productRevenueOriginal * 0.1)` — 1원 단위 반올림.
- `vatAdjustedRevenue = productRevenueOriginal - vatAmount` — 대표 기준 매출.
- **적용 단위**: 판매단위 row 레벨(단독 유닛, 그룹 부모, 그룹 자식 각각 독립 계산).

### 배송비
- 상품별 무료배송 임계액 역산 **금지**.
- 주문 묶음 키 = `packageNumber ?? orderId`.
- `estimatedDeliveryBaseCost = uniquePackageCount * store.deliveryUnitCost`.
- `customerPaidDeliveryFee = Σ orderItem.deliveryFeeAmount`.
- `storeBorneDeliveryCost = Math.max(0, estimatedDeliveryBaseCost - customerPaidDeliveryFee)` — **음수 clamp 0**.
- **적용 단위**: **스토어 레벨(대시보드) 단일**. 판매단위 row에는 배송 필드를 넣지 않음.

### 최종 계산식 (확정)
```
── 판매단위 row ───────────────────────────────────────
row.roughProfit            = row.totalProductRevenue (원본) − row.totalAdCost
row.estimatedNetProfit     = row.vatAdjustedRevenue
                             − row.totalAdCost
                             − row.totalUnitCost
                             − row.totalFeeCost
                             − row.totalOtherCost
                             (배송 미반영)

── 대시보드 (스토어 전체 일별) ──────────────────────
summary.roughProfit        = Σ row.roughProfit
summary.estimatedNetProfit = Σ row.estimatedNetProfit − summary.storeBorneDeliveryCost
```

### 표시
- 화면: 상품매출 원본 / VAT 차감 매출 동시 노출.
- 대시보드 전용: 추정 배송원가 / 고객 실제 부담 배송비 / 스토어 부담 배송비 3개 구분 표시.
- 판매단위별 화면: 배송 지표 표시하지 않음 (스토어 공통 비용).

## 1. 핵심 설계 결정 사항 (이 계획의 기반)

| # | 결정 | 근거 |
|---|------|------|
| 1 | 배송 단가는 스토어별 설정(`stores.deliveryUnitCost: number`), 단일 필드로 전역 적용 | 운영자가 탭에서 직접 조정 가능해야 함 |
| 2 | `storeBorneDeliveryCost`는 0으로 clamp | 도서산간 등으로 고객이 더 냈을 때 순이익 부풀림 방지 |
| 3 | 배송은 **스토어 레벨 단일 계산 함수로 분리**. 판매단위 row 집계에 배송 로직 섞지 않음 | 매핑·롤업 구조에 침투 최소화. 단위별/스토어 합 불일치 자체를 회피 |
| 4 | `roughProfit`은 **VAT 전 상품매출 원본** 기준 | "거친 마진"은 직관적으로 매출 기준. 최종 순이익만 VAT 차감 매출 사용 |
| 5 | 판매단위 row(단독·자식·부모그룹 모두)에 배송 필드 없음. 배송은 대시보드에만 | 3번 결정의 자연 귀결. 자식 안분 귀속의 임의성 회피 |

## 2. 전체 데이터 흐름 변화

### 기존 흐름
```
orderItems
  → calculateDailyProfitRows
      row.totalProductRevenue += item.productPaymentAmount
      row.totalDeliveryFeeAmount += item.deliveryFeeAmount
  → Step 4: totalRevenue = totalProductRevenue
            estimatedNetProfit = totalRevenue − ad − unit − fee − other

calculateDashboardSummary
  → Σ row.*
  → deliveryFeeSummary: { totalDeliveryFeeAmount, includedInEstimatedNetProfit: false }
```

### 신규 흐름
```
orderItems
  → calculateDailyProfitRows
      row.totalProductRevenue += item.productPaymentAmount   (기존 그대로)
      row.totalDeliveryFeeAmount += item.deliveryFeeAmount    (기존 그대로, "고객 부담" 의미)
      ※ packageKeySet / uniquePackageCount 등 배송 관련 상태 없음
  → Step 2 (롤업): 기존 그대로. VAT나 배송 로직 추가 없음
  → Step 3 (광고): 기존 그대로
  → Step 4 (finalize): row 레벨에서 VAT 계산
      row.vatAmount           = Math.round(row.totalProductRevenue * 0.1)
      row.vatAdjustedRevenue  = row.totalProductRevenue − row.vatAmount
      row.totalRevenue        = row.totalProductRevenue       (의미 유지, 하위호환)
      row.roughProfit         = row.totalProductRevenue − row.totalAdCost   (원본 기준)
      row.estimatedNetProfit  = row.vatAdjustedRevenue − ad − unit − fee − other
                                 (배송 미반영)

[독립 신규 함수]
calculateStoreDeliverySummary(database, storeId, dateFrom, dateTo)
  → orderItems 전체 스캔 (storeId, 기간, SALE, 매핑된 것)
  → packageSet = Set<packageNumber ?? orderId>
  → customerPaid = Σ item.deliveryFeeAmount
  → store.deliveryUnitCost 조회
  → { uniquePackageCount, estimatedDeliveryBaseCost,
      customerPaidDeliveryFee, storeBorneDeliveryCost }

calculateDashboardSummary
  → rows = calculateDailyProfitRows(...)
  → Σ row.* (기존처럼)
  → delivery = calculateStoreDeliverySummary(...)
  → summary.estimatedNetProfit = (Σ row.estimatedNetProfit) − delivery.storeBorneDeliveryCost
  → summary의 배송/VAT 필드 모두 채움

profit.service.getDailySalesUnitDetail
  → row.* 그대로
  → revenueBreakdown: { productRevenueOriginal, vatRate, vatAmount, vatAdjustedRevenue }
  → deliveryFeeSummary: 해당 날짜 스토어 전체 배송 요약 (참고용)
                        + 플래그 includedInThisSalesUnitNetProfit: false
```

### 핵심 원칙
- `calculateDailyProfitRows`에는 **VAT 필드만** 추가. 배송 관련 상태(`packageKeySet` 등) 도입하지 않음.
- 배송 계산은 **완전히 독립된 `calculateStoreDeliverySummary` 함수**로 분리.
- 두 계산은 `calculateDashboardSummary`에서만 합쳐짐.

## 3. `Store.deliveryUnitCost` 설정 필드 도입

### 3.1 타입 확장 (`packages/shared/src/types.ts`)
```ts
export interface Store {
  /* ...기존 필드... */
  deliveryUnitCost: number;   // 기본 3500. 0 이상 정수.
}
```
기본값: 3500. 필수 필드(옵셔널 아님)로 두고 마이그레이션에서 일괄 기본값 채움.

### 3.2 마이그레이션 (`database.service.ts`)
`normalizeSnapshot`에 다음 단계 추가:
```ts
draft.stores.forEach((store) => {
  if (typeof store.deliveryUnitCost !== "number" || store.deliveryUnitCost < 0) {
    store.deliveryUnitCost = 3500;
  }
});
```
- PostgreSQL 모드: `payload JSONB`이므로 스키마 변경 없음. 로드 시 자동 보정.
- 파일 모드: 마찬가지로 로드 시 자동 보정.

### 3.3 API (`app.controller.ts` + `store.service.ts`)
- 기존 `PATCH /api/v1/stores/:storeId` 확장하여 `deliveryUnitCost` 필드도 업데이트 가능.
- 검증: `Number.isInteger(value) && value >= 0` (권장 상한 필요하면 100,000 정도).
- 감사 로그: 변경 시 `audit-log.service`에 `STORE_UPDATED`로 기록 (기존 패턴).

### 3.4 부트스트랩 (`environment-bootstrap.service.ts`)
- `createOrUpdateStore` 시 `deliveryUnitCost`가 없으면 3500으로 생성.
- env에 `NAVER_STORE_DELIVERY_UNIT_COST`를 추가할지는 **불요**로 판단 (운영자가 UI에서 조정).

### 3.5 프론트엔드 (`app/(main)/settings/stores/page.tsx`)
- 스토어 설정 패널에 "배송 단가(원)" 숫자 입력 추가. placeholder "3500".
- 저장 시 `PATCH /api/v1/stores/:storeId`로 전송.
- 설정 저장 후 대시보드·손익 수치가 즉시 재계산되어 반영됨을 설명하는 보조 텍스트.

### 3.6 주의점
- **값 변경은 과거 조회 결과에도 영향**을 준다. 히스토리 보존하려면 기간별 설정(effectiveFrom/To) 구조가 필요하지만, 요구사항이 "필드 하나"이므로 현재 값으로 **모든 날짜에 동일하게 적용**. 이 의사결정을 UI에 짧게 안내.

## 5. 핵심 로직 수정 상세 (`apps/backend/src/helpers.ts`)

### 5.1 유틸 함수 신규 추가
파일 내 유틸 섹션(`calculateFee`, `computeProfitStatus` 근처)에 추가:
```ts
import { VAT_RATE } from "@patima/shared";

export const calculateVatAmount = (productRevenue: number): number =>
  Math.round(productRevenue * VAT_RATE);

export const calculateVatAdjustedRevenue = (productRevenue: number): number =>
  productRevenue - calculateVatAmount(productRevenue);

export const resolvePackageKey = (item: OrderItem): string => {
  const trimmed = item.packageNumber?.trim() ?? "";
  return trimmed || item.orderId;
};

export const calculateEstimatedDeliveryBaseCost = (
  uniquePackageCount: number,
  deliveryUnitCost: number,
): number => uniquePackageCount * deliveryUnitCost;

export const calculateStoreBorneDeliveryCost = (
  estimated: number,
  customerPaid: number,
): number => Math.max(0, estimated - customerPaid);
```

> 재활용 원칙: `resolvePackageKey`·VAT 유틸은 테스트·프론트 mock·디버그에서도 동일하게 사용. 인라인 산식(`* 0.1`, `?? orderId`) 금지.

### 5.3 `calculateDailyProfitRows` — Step 1/2/3는 **기존 그대로**
- Step 1(주문 집계), Step 2(롤업), Step 3(광고 귀속)에 **변경 없음**.
- 이 덕분에 `recalculateOrderMappingsForStore`, 롤업 로직, 광고 매핑 엔진 등 주변 코드는 전혀 건드릴 필요 없음.

### 5.4 `calculateDailyProfitRows` — Step 4 (finalize) 수정
공용 mutator 함수로 추출 권장(현재 코드는 `row`와 `childRow` 각각 두 번 계산하는 구조):
```ts
const finalizeRow = (row: DailySalesUnitProfit & { fallbackIncomplete: boolean }) => {
  row.vatAmount = calculateVatAmount(row.totalProductRevenue);
  row.vatAdjustedRevenue = row.totalProductRevenue - row.vatAmount;

  row.totalRevenue = row.totalProductRevenue;                 // 의미 유지
  row.roughProfit = row.totalProductRevenue - row.totalAdCost;  // ← 원본 기준 (§0 확정)
  row.profitStatus = computeProfitStatus(row.fallbackIncomplete);
  row.estimatedNetProfit = row.fallbackIncomplete
    ? null
    : row.vatAdjustedRevenue
      - row.totalAdCost
      - row.totalUnitCost
      - row.totalFeeCost
      - row.totalOtherCost;
};

/* Step 4 */
return Array.from(resultMap.values()).map((row) => {
  finalizeRow(row);
  if (includeGroupChildren && row.isGroup) {
    const groupKey = `${row.date}:${row.canonicalSalesUnitId}`;
    row.childRows = (groupChildrenMap.get(groupKey) ?? [])
      .map((c) => { finalizeRow(c); return c; })
      .sort((a, b) => a.displayName.localeCompare(b.displayName, "ko"));
  }
  return row;
}).sort(...);
```
> 공용 mutator화는 현재 코드 중복(메인 map + childRows map) 문제 해결 목적도 겸함.

### 5.5 `calculateStoreDeliverySummary` 신규 함수
```ts
export interface StoreDeliverySummary {
  uniquePackageCount: number;
  deliveryUnitCost: number;
  estimatedDeliveryBaseCost: number;
  customerPaidDeliveryFee: number;
  storeBorneDeliveryCost: number;
}

export const calculateStoreDeliverySummary = (
  database: DatabaseShape,
  storeId: string,
  dateFrom: string,
  dateTo: string,
): StoreDeliverySummary => {
  const store = database.stores.find((s) => s.id === storeId);
  const deliveryUnitCost = store?.deliveryUnitCost ?? DEFAULT_DELIVERY_UNIT_COST;

  const packageSet = new Set<string>();
  let customerPaidDeliveryFee = 0;

  database.orderItems
    .filter((item) =>
      item.storeId === storeId &&
      item.paymentDate &&
      item.paymentDate >= dateFrom &&
      item.paymentDate <= dateTo &&
      item.saleStatus === "SALE" &&
      item.canonicalSalesUnitId,       // ← 매핑된 것만 포함 (UNMAPPED 제외)
    )
    .forEach((item) => {
      packageSet.add(resolvePackageKey(item));
      customerPaidDeliveryFee += item.deliveryFeeAmount ?? 0;
    });

  const uniquePackageCount = packageSet.size;
  const estimatedDeliveryBaseCost = calculateEstimatedDeliveryBaseCost(
    uniquePackageCount,
    deliveryUnitCost,
  );
  const storeBorneDeliveryCost = calculateStoreBorneDeliveryCost(
    estimatedDeliveryBaseCost,
    customerPaidDeliveryFee,
  );

  return {
    uniquePackageCount,
    deliveryUnitCost,
    estimatedDeliveryBaseCost,
    customerPaidDeliveryFee,
    storeBorneDeliveryCost,
  };
};
```

### 5.6 `calculateDashboardSummary` 수정
```ts

/* 신규: 스토어 레벨 배송 */
const deliverySummary = calculateStoreDeliverySummary(database, storeId, date, date);

/* 최종 순이익 = 판매단위 순이익 합 − 스토어 부담 배송비 */
const sumRowNetProfit = rows.reduce(
  (s, r) => s + (r.estimatedNetProfit ?? 0), 0,
);
const finalEstimatedNetProfit = incompleteRowCount > 0
  ? null
  : sumRowNetProfit - deliverySummary.storeBorneDeliveryCost;
```

## 6. 설계상 남아있는 주의점

### 6.1 그룹 자식/부모 VAT 값 관찰
- 부모 row의 `totalProductRevenue`는 자식들의 raw 합이라 정확.
- 부모 `vatAmount = round(부모합 * 0.1)`. 자식들은 각자 `round(자식합 * 0.1)`.
- **Σ 자식 vatAmount ≠ 부모 vatAmount**일 수 있음(반올림 차이 ±N원).
- UI에서 자식 vatAmount를 단순 합산하여 부모와 일치할 거라고 기대하면 안 됨 → 화면 설계 시 "VAT는 각 row 개별 반올림"이라는 안내 필요.

### 6.2 `storeBorneDeliveryCost` 음수 clamp
- `Math.max(0, …)`. 현재 계획서의 공식 확정.
- clamp된 경우 "고객 결제분이 추정 원가를 초과함"이라는 상황이며, 대시보드 UI에 해당 일자가 clamp된 상태인지 hover/뱃지로 보여줄지 검토(선택).

### 6.3 취소/반품 주문의 묶음 처리
- 현재 계산은 `saleStatus === "SALE"`만 포함 → 묶음 집합에도 자동 제외.
- 요구사항의 "실제 발송되는 묶음" 의미와 부합. 유지.

### 6.4 `packageNumber` 공백/누락
- `resolvePackageKey`에서 trim 후 빈 문자열이면 `orderId`로 폴백.
- 한 `orderId` 내 일부 아이템만 `packageNumber`가 있는 혼재 케이스: null은 `orderId`로 묶여 **실제보다 묶음 수가 적어질 수 있음**. 요구사항이 명시한 규칙이므로 그대로 둠. 플래그 집계는 도입 안 함.

### 6.5 매핑되지 않은(UNMAPPED/CONFLICT) 주문의 배송 취급
- `calculateStoreDeliverySummary`는 `item.canonicalSalesUnitId`가 있는 것만 포함(매핑되지 않은 주문 제외).
- 이유: 대시보드의 `Σ row.estimatedNetProfit`이 매핑된 주문에서만 생성되므로, 배송도 동일 모집단을 써야 차감이 일관.
- 대안(미채택): "발송은 되었지만 매핑이 안 된 주문"도 배송원가에 포함 → 매핑 복구 시 배송비가 변해버리는 혼란. 취소.

### 6.6 `deliveryUnitCost` 변경의 과거 영향
- 현재 스토어 값 하나로 모든 기간에 적용. 과거 대시보드 조회 결과도 즉시 변함.
- 히스토리 보존이 필요해지면 별도 ticket으로 기간별 설정 도입.

## 9. 테스트 계획 (`apps/backend/src/run-tests.ts`)

### 9.1 유틸 단위
- `calculateVatAmount(10_000) === 1_000`
- `calculateVatAmount(9_994) === 999` (0.5 미만 내림)
- `calculateVatAmount(9_995) === 1_000` (0.5 은행가 반올림 주의 — JS `Math.round`는 half-up)
- `calculateVatAdjustedRevenue(10_000) === 9_000`
- `resolvePackageKey({ packageNumber: "P1", orderId: "O1" }) === "P1"`
- `resolvePackageKey({ packageNumber: "  ", orderId: "O1" }) === "O1"` (공백 trim 후 폴백)
- `resolvePackageKey({ packageNumber: null, orderId: "O1" }) === "O1"`
- `calculateStoreBorneDeliveryCost(7000, 3000) === 4000`
- `calculateStoreBorneDeliveryCost(3500, 5000) === 0` (clamp)

### 9.2 `calculateDailyProfitRows` — VAT 관점
1. 단일 row: `totalProductRevenue=10,000` → `vatAmount=1000`, `vatAdjustedRevenue=9000`, `estimatedNetProfit = 9000 − ad − unit − fee − other`.
2. `roughProfit`이 원본 매출 기준인지 확인: `roughProfit = 10,000 − totalAdCost`.
3. 자식 A=9,995 / 자식 B=9,995 → 부모 `totalProductRevenue=19,990`, 부모 `vatAmount=round(1,999)=1,999`. 자식 각자 `vatAmount=round(999.5)=1,000` → Σ 자식 vatAmount=2,000 vs 부모=1,999. **불일치 ±1원을 기대값으로** 박아 테스트.
4. `fallbackIncomplete=true`이면 `estimatedNetProfit === null` 유지.
5. 배송 관련 필드 **없음** 재확인(`"uniquePackageCount" in row === false`).

### 9.3 `calculateStoreDeliverySummary` — 독립 테스트
1. 같은 묶음 2아이템(P1): `uniquePackageCount=1`, estimated=3500.
2. 서로 다른 묶음 2건(P1, P2): count=2, estimated=7000.
3. `packageNumber` 누락 & 다른 `orderId`: count=2.
4. `packageNumber` 누락 & 같은 `orderId`: count=1.
5. 매핑되지 않은(`canonicalSalesUnitId=null`) 아이템은 집합에서 제외.
6. `saleStatus="CANCELED"` 아이템 제외.
7. 기간 필터 정확: `dateFrom/dateTo` 밖의 아이템 제외.
8. `store.deliveryUnitCost`가 5000인 스토어: estimated가 count * 5000으로 반영.
9. `store.deliveryUnitCost` 미설정(또는 undefined): 3500 기본값 사용.
10. `storeBorneDeliveryCost` clamp: 고객부담 > 추정 → 0.

### 9.4 `calculateDashboardSummary`
1. 판매단위 2개, 같은 묶음 P1 공유: row 합 vs dashboard 불일치 구조가 **이제 row에 없으므로** 문제 자체 소멸. dashboard `uniquePackageCount=1`만 검증.
2. `estimatedNetProfit = Σ row.estimatedNetProfit − storeBorneDeliveryCost` 공식 검증.
3. `incompleteRowCount > 0`이면 `estimatedNetProfit === null`(기존 정책 유지) 검증.
4. `totalVatAmount`, `totalVatAdjustedRevenue`가 row 합과 일치 (동일 모집단이므로 일치).

### 9.5 `profit.service.getDailySalesUnitDetail`
1. 응답에 `revenueBreakdown` 포함, `vatRate=0.1` 고정.
2. 응답에 `deliveryContext` 포함, `includedInThisSalesUnitNetProfit === false` 고정.
3. `deliveryContext`의 값들이 `calculateStoreDeliverySummary(storeId, date, date)`와 일치.
4. `summary.estimatedNetProfit`에는 배송이 반영되지 않음(판매단위 순이익).

### 9.6 `Store.deliveryUnitCost` CRUD
1. `PATCH /stores/:id { deliveryUnitCost: 5000 }` → 응답 200, 스냅샷 반영.
2. `deliveryUnitCost: -1` → 400 검증 에러.
3. `deliveryUnitCost: 1.5` → 400(정수 검증) or 반올림 정책 결정(현재 정수 검증 권장).
4. 마이그레이션: 기존 스토어 `deliveryUnitCost` 없는 레코드 로드 → 3500으로 보정 확인.
