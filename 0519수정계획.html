0519 수정계획: 매핑 화면 서버 페이지네이션 완성

0518 성능 구조 개선으로 주문/광고 원장 전체 fetch는 끊었지만, 매핑 화면에는 아직 서버 페이지네이션 UI와 서버 검색이 완성되지 않았다. 현재 화면은 일부 첫 페이지 묶음만 가져와 병합하므로 고유 시그니처가 200건을 넘으면 나머지 항목을 탐색할 수 없다. 이 문서는 다음 세션이 매핑 화면 페이지네이션을 안전하게 완성하기 위한 인수인계 문서다.

1. 현재 상태 요약

0518 작업으로 매핑 구조는 원장 row 중심에서 시그니처 중심으로 이동했다. 주문은 orderSourceSignatures, 광고는 새로 도입된 adCampaignSignatures가 매핑 관리 대상이다. orderItems와 adCampaignDailyCosts는 손익 계산을 위한 원장으로 계속 유지한다.

이미 반영된 것

  • 주문 동기화 후 전체 주문 아이템 재계산 대신 touched item 중심 증분 매핑을 사용한다.
  • 주문 시그니처에 usageCount, firstSeenAt, lastSeenAt, sample ID 필드가 추가됐다.
  • 광고 캠페인 시그니처 AdCampaignSignature가 추가됐다.
  • 광고 수동 매핑은 시그니처에 저장되고, row에는 스냅샷으로 반영된다.
  • 캠페인 규칙 변경 기본 경로는 과거 광고 원장 row를 바로 덮지 않고 signature만 재계산한다.

아직 미완성인 것

  • 매핑 화면의 주문/광고 목록에 서버 페이지 이동 UI가 없다.
  • 검색어 입력이 서버 q 파라미터로 연결되지 않고, 현재 로딩된 배열 안에서만 검색된다.
  • 현재 프론트는 첫 페이지 몇 묶음을 가져와 병합하므로 200건 밖 항목은 UI에서 접근할 수 없다.
  • 전체 개수, 현재 페이지, 총 페이지, 다음/이전 페이지 상태가 화면에 표시되지 않는다.
중요: 주문 원장 400건이 200건으로 삭제되거나 압축된 것이 아니다. 매핑 화면은 원장 row가 아니라 고유 시그니처 목록을 보여준다. 다만 고유 시그니처 자체가 200건을 넘으면 현재 UI에서는 뒤 페이지를 볼 수 없다.

2. 문제 정의

현재 apps/frontend/lib/api/services.ts의 getMappingsPageData는 매핑 화면 초기 데이터를 만들 때 전체 페이지를 끝까지 가져오지 않도록 수정되어 있다. 대신 주문과 광고 각각 다음과 같은 첫 페이지만 가져온다. 

// 현재 취지
주문: ALL page 1 + UNMAPPED page 1 + CONFLICT page 1
광고: ALL page 1 + UNMAPPED page 1 + CONFLICT page 1

이 방식은 전체 fetch를 끊는 임시 bridge로는 유효하지만, 실제 운영 화면으로는 부족하다. 사용자가 2페이지 이후의 시그니처를 검색하거나 수동 매핑할 수 없고, "목록이 줄었다" 또는 "일부 항목이 사라졌다"처럼 보인다.

구분 현재 동작 문제
주문 시그니처 /order-source-signatures?page=1&pageSize=200 중심 2페이지 이후 항목을 볼 UI가 없다.
광고 시그니처 /ad-campaign-signatures?page=1&pageSize=200 중심 매핑 완료/미매핑/충돌 전체 탐색이 제한된다.
검색 프론트 배열 필터 서버에 있는 2페이지 이후 데이터는 검색되지 않는다.
선택 현재 로딩된 행 ID만 선택 가능 페이지 이동 시 선택 유지 정책이 정의되어 있지 않다.

3. 목표

매핑 화면의 주문/광고 목록을 서버 페이지네이션 기반으로 전환한다. 전체 fetch는 다시 도입하지 않는다. 사용자가 페이지를 이동하거나 검색어/필터를 바꾸면 서버 API를 다시 호출해서 해당 페이지를 가져와야 한다.

  • 주문 시그니처 목록은 GET /order-source-signatures의 page, pageSize, mappingStatus, q를 사용한다.
  • 광고 시그니처 목록은 GET /ad-campaign-signatures의 page, pageSize, mappingStatus, q를 사용한다.
  • 프론트 UI에 현재 페이지, 총 개수, 이전/다음 버튼, pageSize 선택을 추가한다.
  • 검색어 입력은 debounce 후 URL query 또는 client state를 통해 서버 요청에 반영한다.
  • 페이지 이동 후에도 이미 선택한 항목을 유지할지, 현재 페이지 선택만 유지할지 정책을 명확히 한다.
완료 기준: 고유 주문/광고 시그니처가 200건을 넘어도 사용자가 페이지 이동과 서버 검색으로 모든 항목을 찾고 매핑할 수 있어야 한다.

5. 권장 데이터 구조

프론트 MappingsPageData에 주문/광고 각각의 페이지 정보를 별도로 추가한다. 기존 signatures, adCosts 배열은 유지하되, metadata를 함께 내려서 컴포넌트가 컨트롤을 그릴 수 있게 한다. 

export interface PageMeta {
  page: number;
  pageSize: number;
  totalCount: number;
  totalPages: number;
  hasNext: boolean;
}

export interface MappingListState {
  mappingStatus: "ALL" | "MAPPED" | "UNMAPPED" | "CONFLICT";
  q: string;
  page: number;
  pageSize: number;
}

export interface MappingsPageData {
  primaryStore: StoreListItem | null;
  salesUnits: SalesUnitListItem[];
  signatures: OrderSourceSignatureListItem[];
  signaturePage: PageMeta;
  signatureQuery: MappingListState;
  adCosts: CampaignCostListItem[];
  adCostPage: PageMeta;
  adCostQuery: MappingListState;
  campaignMappings: CampaignMappingRuleListItem[];
  sources: SourceState[];
}

이름은 꼭 위와 같을 필요는 없지만, 주문과 광고의 page/query 상태를 분리해야 한다. 두 목록은 독립적으로 페이지 이동할 수 있어야 하기 때문이다.

6. URL Query 설계

매핑 화면은 새로고침해도 같은 목록 상태를 복원할 수 있도록 URL query를 사용하는 것을 권장한다. 주문과 광고 query가 충돌하지 않도록 prefix를 분리한다.

Query 의미 기본값
orderPage 주문 시그니처 현재 페이지 1
orderPageSize 주문 시그니처 페이지 크기 100 또는 200
orderStatus 주문 매핑 상태 필터 ALL
orderQ 주문 서버 검색어 빈 문자열
adPage 광고 시그니처 현재 페이지 1
adPageSize 광고 시그니처 페이지 크기 100 또는 200
adStatus 광고 매핑 상태 필터 ALL
adQ 광고 서버 검색어 빈 문자열
필터나 검색어가 바뀌면 해당 목록의 page는 1로 되돌리는 것이 안전하다. 예를 들어 orderQ가 바뀌면 orderPage=1로 변경한다.

7. 프론트 구현 계획

7.1 page.tsx에서 searchParams 전달

apps/frontend/app/(main)/mappings/page.tsx가 현재 storeId 정도만 넘긴다면, 주문/광고 page/query 값을 파싱해서 getMappingsPageData에 전달하도록 바꾼다. 

const data = await getMappingsPageData({
  storeId,
  order: {
    page: Number(searchParams.orderPage ?? 1),
    pageSize: Number(searchParams.orderPageSize ?? 100),
    mappingStatus: parseMappingStatus(searchParams.orderStatus),
    q: String(searchParams.orderQ ?? ""),
  },
  ad: {
    page: Number(searchParams.adPage ?? 1),
    pageSize: Number(searchParams.adPageSize ?? 100),
    mappingStatus: parseMappingStatus(searchParams.adStatus),
    q: String(searchParams.adQ ?? ""),
  },
});

7.2 services.ts에서 단일 페이지만 호출

현재 getMappingsPageData는 임시로 ALL + UNMAPPED + CONFLICT 첫 페이지를 병합한다. 페이지네이션 완성 후에는 이 병합을 제거하고, 사용자가 선택한 필터의 단일 페이지만 가져와야 한다. 

const [signatureResponse, adCostResponse, campaignMappingResponse] = await Promise.all([
  getOrderSourceSignatures(primaryStore.id, {
    mappingStatus: order.mappingStatus,
    q: order.q,
    fetchAll: false,
    page: order.page,
    pageSize: order.pageSize,
  }),
  getAdCampaignSignatures(primaryStore.id, salesUnitResponse.data, {
    mappingStatus: ad.mappingStatus,
    q: ad.q,
    page: ad.page,
    pageSize: ad.pageSize,
  }),
  getCampaignMappings(primaryStore.id, salesUnitResponse.data),
]);

7.3 fetchRecordPage가 metadata를 보존하도록 수정

현재 fetchRecordPage는 response.data.items만 data로 반환한다. 페이지 UI를 위해 page, pageSize, totalCount, totalPages, hasNext를 함께 보존해야 한다. 

return {
  ...response,
  data: response.data.items,
  page: {
    page: response.data.page ?? params.page ?? 1,
    pageSize: response.data.pageSize ?? params.pageSize ?? MAX_FRONTEND_PAGE_SIZE,
    totalCount: response.data.totalCount ?? response.data.items.length,
    totalPages: response.data.totalPages ?? 1,
    hasNext: response.data.hasNext ?? false,
  },
};

7.4 MappingsView에 컨트롤 추가

주문 패널과 광고 패널 각각에 상태 필터, 검색 입력, 이전/다음 버튼, pageSize 선택을 추가한다. 기존 showOnlyUnmappedOrders, showOnlyUnmappedAds 체크박스는 서버 필터와 역할이 겹치므로 제거하거나 mappingStatus 선택 UI로 바꾸는 것이 좋다.

  • 상태 필터: ALL, UNMAPPED, CONFLICT, MAPPED
  • 검색 입력: submit 또는 debounce 후 URL query 갱신
  • 페이지 버튼: 이전/다음, 처음/끝은 선택
  • 카운터: 총 N건 / P of T 페이지
  • pageSize: 50, 100, 200 중 선택

8. 백엔드 확인 사항

백엔드는 이미 기본적인 page/q/status를 지원한다. 그래도 다음을 반드시 확인해야 한다.

8.1 주문 시그니처 API

  • GET /api/v1/order-source-signatures가 page, pageSize, mappingStatus, q를 모두 받는다.
  • listOrderSourceSignatures는 전체 filtered 목록을 만든 뒤 paginate하고, 해당 page의 enrichment만 수행한다.
  • 응답에는 items뿐 아니라 page, pageSize, totalCount, totalPages, hasNext가 있어야 한다.
  • usageCount가 기존 snapshot에서 비어 있어도 현재 page 관련 orderItems로 보정된다.

8.2 광고 시그니처 API

  • GET /api/v1/ad-campaign-signatures가 page, pageSize, mappingStatus, q를 모두 받는다.
  • 매핑 완료 항목도 mappingStatus=ALL 또는 MAPPED에서 조회되어야 한다.
  • 삭제된 upload의 row는 active upload 기준 목록에서 빠져야 한다.
  • signature summary가 stale하지 않도록 삭제 경로에서 refreshAdCampaignSignatureSummaries가 호출된다.

9. 선택 유지 정책

페이지네이션을 붙이면 선택 상태 정책을 반드시 정해야 한다. 기존 화면은 현재 로딩된 배열 안에서 선택 ID를 유지한다. 서버 페이지네이션에서는 다음 두 방식 중 하나를 택한다.

방식 장점 단점
페이지 이동 시 선택 초기화 구현 단순, 사용자가 실수로 숨은 선택을 매핑할 위험이 작다. 여러 페이지에서 모아 선택하는 작업은 불가능하다.
페이지 이동 후에도 선택 유지 여러 페이지 항목을 한 번에 매핑할 수 있다. 숨겨진 선택 개수 표시와 해제 UI가 꼭 필요하다.
권장 1차 구현은 "페이지/검색/필터 변경 시 선택 초기화"다. 기존 hidden selected UI를 유지하려면 복잡도가 올라가므로, 먼저 단순하고 안전한 정책으로 시작하는 편이 좋다.

11. 주의점

  • 전체 fetch 부활 금지: fetchAllRecordPages를 매핑 화면 기본 로딩에 다시 사용하면 0518 개선 목적이 무너진다.
  • 원장 row 삭제 금지: 페이지네이션은 UI 조회 방식 변경일 뿐, orderItems나 adCampaignDailyCosts를 줄이는 작업이 아니다.
  • 시그니처 기준 유지: 광고 매핑 화면은 일별 광고 row가 아니라 adCampaignSignatures를 보여주는 방향을 유지한다.
  • 검색은 서버에서: 프론트 배열 필터만으로는 2페이지 이후 항목을 찾을 수 없다. 반드시 API q에 연결한다.
  • 필터와 page 리셋: 검색어, 상태 필터, pageSize가 바뀌면 해당 목록 page를 1로 되돌린다.
  • 선택 상태: 페이지 이동 시 선택을 유지한다면 숨겨진 선택을 명확히 보여주고 일괄 해제 버튼을 제공해야 한다.
  • 수동 매핑 우선: confirmedAt 있는 주문/광고 시그니처는 자동 재계산이 덮지 않아야 한다.
  • 광고 과거 row 반영 주의: 캠페인 규칙 변경만으로 과거 adCampaignDailyCosts row를 일괄 수정하지 않는다.

    1차 구현에서는 페이지/검색/필터 변경 시 선택을 초기화하는 정책을 권장한다.
  7. 테스트 추가
    백엔드 목록 API page/q/status 테스트를 추가하고, 프론트 typecheck를 통과시킨다.
  8. 검증
    npm.cmd run test --workspace @patima/backend, npm.cmd run lint 실행.

13. 완료 기준

  • 매핑 화면에서 주문 시그니처 200건 이후 페이지로 이동할 수 있다.
  • 매핑 화면에서 광고 캠페인 시그니처 200건 이후 페이지로 이동할 수 있다.
  • 서버 검색으로 현재 로딩되지 않은 페이지의 항목도 찾을 수 있다.
  • 상태 필터 ALL, MAPPED, UNMAPPED, CONFLICT가 주문/광고 모두 정상 동작한다.
  • 페이지 이동/검색/필터 변경 시 선택 상태가 의도한 정책대로 정리된다.
  • 수동 매핑 저장 후 현재 페이지 데이터가 최신 상태로 refresh된다.
  • 기존 손익 계산 결과는 변하지 않는다.
  • 매핑 화면 기본 진입에서 전체 페이지를 끝까지 fetch하지 않는다.
